# 任务 UI 重构规划

## 1. 目标

本次重构的目标不是继续修补当前任务 UI，而是把它收敛成一套联机稳定、职责清晰、便于继续扩展的架构。

最终目标：

- 任务 UI 只有一个全局管理器
- 任务 UI 的所有结构和槽位都预设好
- 任务内容的注册、更新、替换全部走全局同步链
- 玩家本地交互只做显示/隐藏、页切换、详情切换、位置切换
- 本地链不再创建/销毁/注册/重建任务 UI 内容
- 本地链不再修改挂着 frame handle 的共享运行时 table

一句话：

`任务内容是全局同步的，任务界面的交互显示是本地的。`

---

## 2. 当前问题总结

当前版本已经证明：

- 纯 `J` 开关基本稳定
- 纯本地 `false` 注册本身不是唯一问题
- 真正高危的是本地高频交互链里：
  - 修改共享状态
  - 立即触发整页刷新
  - 写回持有 frame handle 的长生命周期 table

当前已经暴露出的风险点：

1. 本地链修改单例状态
- `currentCategory`
- `currentPage`
- `expandedQuestId`
- `previousCategory`
- `previousPage`

2. 本地链修改 frame-tree bookkeeping
- `page.visibleVariantIndex`
- `categoryView.lastShownPageIndex`

3. 本地链调用渲染函数时，仍然会做成组的显隐切换

4. 任务 UI 逻辑仍然带着“状态机 + 立即渲染”的旧模型

当前根因结论：

- 不是单个 API 的 `false`/`true` 选择问题
- 是“本地交互链仍然在改共享运行时状态并立刻消费”的架构问题

---

## 3. 最终架构原则

### 3.1 全局同步层负责什么

全局同步层负责：

- 接受任务
- 完成任务
- 放弃任务
- 任务目标进度更新
- 任务标题/描述/奖励/图标/状态更新
- 哪些任务应出现在主线/支线/小任务中
- 哪些预设槽位应显示哪条任务内容
- 任务 UI 预设页的数据填充

这些操作允许做：

- 创建/初始化任务 UI 数据模型
- 更新预设槽位的文本、贴图、数据绑定
- 低频刷新整页预设内容

这些操作不允许放在本地交互链里。

### 3.2 本地交互层负责什么

本地交互层只负责：

- `J` 开关面板
- 切主线/支线/小任务
- 切分页
- 展开/收起任务详情
- 滚轮切页
- 滑块位置变化
- show/hide 已预设好的 frame
- 必要的位置切换
- 本地点击音效

本地交互层不允许：

- 创建 frame
- 销毁 frame
- 注册/反注册任务内容
- 重建 page / variant / row 结构
- 改任务数据源
- 改共享运行时映射结构
- 改挂着 frame handle 的 table bookkeeping
- 在本地链里做同步探针

### 3.3 设计边界

严格采用：

- `内容更新：全局同步`
- `视觉交互：本地显示`

不要再采用：

- `内容也在本地交互链里刷新`
- `本地交互顺手改状态树，再立即重渲`

---

## 4. 核心设计

### 4.1 顶层结构

保留单例：

```ts
class TaskUIManager
```

职责：

- 初始化所有任务 UI 预设结构
- 持有全局唯一任务 UI frame 树
- 维护当前预设内容模型
- 对外暴露：
  - 全局内容更新接口
  - 本地显示控制接口

### 4.2 两层数据模型

#### A. 全局内容模型

新建一套面向 UI 的全局内容快照，例如：

```ts
interface TaskUIViewContentSnapshot {
  categories: Record<QuestType, TaskUICategoryContent>;
}

interface TaskUICategoryContent {
  pages: TaskUIPageContent[];
}

interface TaskUIPageContent {
  rows: TaskUIRowContent[];
}

interface TaskUIRowContent {
  questId: string;
  title: string;
  statusText: string;
  iconPath: string;
  objectives: string[];
  failText: string;
  detailLines: string[];
}
```

这套内容模型只在全局同步链更新。

#### B. 本地视图选择状态

本地只保留极轻量的“当前正在看哪块”：

```ts
interface TaskUIViewSelection {
  visible: boolean;
  category: QuestType;
  pageIndex: number;
  expandedRowIndex: number; // -1 表示未展开
}
```

注意：

- 这套状态只用于“选中哪块预设内容”
- 不再参与内容生成
- 不再回写 page/category 运行时 table

---

## 5. 必须删除的旧模式

以下模式在重构时必须移除：

1. 在本地链里写：
- `page.visibleVariantIndex`
- `categoryView.lastShownPageIndex`

2. 在本地链里调用“全量重建”：
- `rebuildPages()`
- `rebuildTaskUIFacadeListPool(...)`

3. 在本地链里根据当前状态再重算任务内容

4. 在本地链里创建/清空/重写 `questIds`、`variants`、`pages`

5. 任何“入口改状态 -> 立即整页渲染”的模式

6. 任何额外同步探针、临时 handle 创建、调试输出残留

---

## 6. 预设 UI 模型

### 6.1 预设内容树

初始化阶段一次性创建：

- 主面板
- 分类根
- 每个分类的 page 根
- 每个 page 的默认折叠 variant
- 每个 page 的展开 variant 集合
- 每个 row 的标题、图标、按钮、目标文本、详情文本
- 滚动条、滑块、滑块命中层

要求：

- 不在交互时 `ensurePage`
- 不在交互时补建 `variant`
- 不在交互时补建 `row slot`

### 6.2 内容填充方式

全局同步链收到任务数据变化时：

- 重新计算 `TaskUIViewContentSnapshot`
- 把预设槽位文本/贴图/详情一次性写好

本地交互时：

- 只切 root / variant 的显隐
- 不再改内容文本

---

## 7. 事件与输入规则

### 7.1 鼠标与键盘输入

允许：

- 鼠标 `sync=false`
- 键盘 `sync=false`

前提：

- 底层封装必须先包本地玩家判断
- `Trg` 入口视为同步，不参与这一层包装

### 7.2 后续逻辑统一

所有输入必须汇入统一的本地后续函数，例如：

- `togglePanelLocal()`
- `switchCategoryLocal(type)`
- `switchPageLocal(pageIndex)`
- `toggleExpandLocal(rowIndex)`

不要保留：

- 鼠标一套逻辑
- 键盘另一套逻辑

### 7.3 事件回调形式

优先：

- 模块级命名函数
- 单列分发

减少：

- 高频匿名闭包直接塞进 JASS 回调

---

## 8. 渲染策略重构

### 8.1 不再“按状态重渲整棵树”

放弃当前模式：

- `flushViewState()`
- `requestRender(VIEW_RENDER_XXX)`
- `applyTaskUIFacadeVisibleState()`
- `applyTaskUICategorySwitchVisibleState()`
- `applyTaskUIPageSwitchVisibleState()`
- `applyTaskUIExpandVisibleState()`

这些函数的职责太偏“状态机重渲染”。

### 8.2 改成“目标块直接切换”

重构为更直接的命令式显示：

- 切分类：
  - hide 旧分类 root
  - show 新分类 root
  - show 新分类当前页 root
  - show 新分类当前页默认 variant

- 切页：
  - hide 当前页 root
  - hide 当前页所有 variant
  - show 目标页 root
  - show 目标页默认 variant

- 展开：
  - hide 当前页默认 variant
  - show 当前页目标展开 variant

- 收起：
  - hide 当前页当前展开 variant
  - show 当前页默认 variant

重点：

- 尽量不扫“所有分类”
- 尽量不扫“所有页”
- 尽量不扫“所有 variant”
- 直接切当前目标块

## 10. 重构实施顺序

### 阶段 1：冻结现有危险逻辑

先做：

- 不再继续修补旧 `flushViewState`
- 不再给旧状态机上补更多特判
- 保留当前可运行版本作对照

### 阶段 2：搭新预设结构

实现：

- 全分类 page/variant/row 一次性预建
- 不接旧交互

验证：

- 面板能正常打开/关闭
- 默认页显示正确

### 阶段 3：接全局内容更新

实现：

- 任务数据变化时更新预设内容

验证：

- 接任务/完成任务后，预设内容正确变化
- 本地不需要重建结构

### 阶段 4：接本地分类切换

实现：

- 只切分类 root/page root/default variant

验证：

- 鼠标点标签、键盘 `1/2/3` 长时间稳定

### 阶段 5：接本地展开详情

实现：

- 当前页默认 variant / 展开 variant 互切

验证：

- 疯狂点任务详情长时间稳定

### 阶段 6：接滚轮翻页

实现：

- 当前分类下旧页 / 新页增量切换
- 滑块位置联动

验证：

- 疯狂滚轮长时间稳定

### 阶段 7：接滑块拖拽

实现：

- 仅任务 UI 使用
- 保持输入链尽量本地

验证：

- 拖拽长时间稳定

## 11. 验收标准

### 必须通过

1. 开局默认隐藏正确  
2. 第一次按 `J` 就能正确显示内容  
3. 第二次按 `J` 能正确关闭  
4. 键盘 `1/2/3` 狂按长时间不掉线  
5. 鼠标点标签狂点长时间不掉线  
6. 任务展开狂点长时间不掉线  
7. 滚轮狂滚长时间不掉线  
8. 本地交互不再触发结构重建  
9. 本地链不再写 frame-tree bookkeeping table  

### 必须代码层满足

1. 本地交互链不再调用 `rebuildPages()`  
2. 本地交互链不再创建/销毁任务 UI frame  
3. 本地交互链不再写：
- `page.visibleVariantIndex`
- `categoryView.lastShownPageIndex`

4. 任务内容更新只走全局同步链  
5. 预设结构创建只在初始化阶段发生一次  

---

## 12. 禁止回退的错误方向

禁止再做：

- 继续给旧 `flushViewState` 增加新 render mode
- 继续靠节流/防抖硬压问题
- 继续在本地链里补更多 `previousXxx`
- 继续把 `pagesDirty`、`rebuildPages` 混回交互链
- 继续在本地链里写 page/category bookkeeping
- 继续使用异步探针排查任务 UI 主链

---

## 13. 结论

当前任务 UI 的真正问题，不是单个 API 是否 `false`，而是：

- 本地交互链仍然在改共享状态
- 本地交互链仍然在消费并写回持有 frame handle 的对象树
- UI 仍然按“状态机 + 立即渲染”模型运行

正确终版方向是：

- 全预设
- 全局内容更新
- 本地只做显示/隐藏与位置切换

执行时请严格按照本文档的阶段顺序推进，不要再回到“边测边补丁修”的路径。
