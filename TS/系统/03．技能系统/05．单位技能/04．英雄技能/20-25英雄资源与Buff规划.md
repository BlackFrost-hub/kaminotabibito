## 1. 资源规划原则

### 1.1 Buff 图标和内部状态分开

只有下面几类状态进入玩家可见 Buff 图标：

- 会改变下一次技能或普攻选择的状态。
- 有叠层、剩余次数或明显持续时间，需要玩家持续判断的状态。
- 会被后续技能主动读取，且玩家需要知道是否已经准备好的状态。
- 真实的护盾、控制、姿态、区域保护或强化窗口。

下面这些不单独制作 Buff 图标：

- 单次技能内部的二段窗口、蓄力帧、斩击阶段和命中去重键。
- 节点、冰晶、剑痕、路线、花田等已经有世界坐标特效表达的场景实体。
- 连接、读取锁、目标引用、一次性消费标记等纯内部数据。
- 仅用于异步回调清理的技能实例字段。

Buff 表、运行时效果、原生魔法效果和 UI 不是同一层。后续落地时不能只生成图标或只登记 `Buff 表`，必须同步确认真实效果、持续时间、叠层、驱散、清理和读取入口。

### 1.2 特效资源先复用，未确认不写死路径

每个特效制作前都必须按以下顺序处理：

1. 搜索 `imports\\Common\\Effect` 和 `.cursor/rules/resources/visual/effect-asset-catalog/` 中的已确认资源。
2. 对外部候选检查模型外观、完整 SHA-256、MDX 内部贴图路径和原生贴图依赖。
3. 能复用就复用，必要时只通过运行时缩放、朝向或改色区分用途。
4. 确实缺失时再生成或迁入，并在资源库登记真实外观、用途、字节数和 SHA-256 前 16 位。
5. AI 生成资源在用户确认前只放临时资源目录，不得直接放入 `imports/`，也不得接入技能配置。

不要为每一个表现层强行制作一个模型。弹道、命中、持续层、范围提示和结束层应按真实生命周期拆分；同一模型可以服务多个技能，但必须在文档中记录适用场景和限制。

### 1.3 图标生成统一要求

后续技能图标和 Buff 图标统一按以下规格准备：

- 先生成 1K 正方形源图，再按项目图标尺寸等比例缩放。
- 采用魔兽风格的白银原生外框；不得在后处理或模型模板中重复叠加第二层外框。
- 主体轮廓必须在缩小后仍可识别，不依赖小字、技能名称或复杂背景表达差异。
- 先判断图标是否属于动作型语义。拔刀、居合、招架、突进、施法、飞行、变身、蓄势和反击等技能或状态，优先使用角色人物轮廓和正确招式姿势；层数、标记、护盾、减益和资源状态等可由状态符号表达，不强行塞入人物。
- 动作型图标输出 `100x100`；普通状态符号图标输出 `80x80`。两者都必须检查缩小后的轮廓、武器方向和语义可读性。
- 动作型图标必须锁定角色参考：服装、发型、武器类型、握持方式、身体朝向、主色和招式来源不得被生图模型自由改写。和装/太刀角色必须保持和装、袖摆、腰带与合理的拔刀/收刀/招架姿势。
- 严禁为制造“战斗感”加入铠甲、肩甲、头盔、战场、军旗、战争女神/女武神、现代军装、额外武器或额外角色。参考资料不足以确认上述内容时，停止生成并先补充确认，不得自行猜测。
- 同一英雄先生成一张动作型图标作为风格样例，用户确认后再批量生成；失败候选不登记正式资源库。Buff 图标和技能图标均适用本条规则。
- 同一英雄使用稳定的主色和材质语言，但相邻状态必须用轮廓、方向或符号区分。
- 正式接入前仍需按图标贴图/模型规则检查透明、BLP 编码、路径和游戏内显示；本规划不预填不存在的图标路径。

## 2. 总量与批次

| 资源类别 | 规划数量 | 说明 |
| --- | ---: | --- |
| Buff 图标 | 30 | 六名英雄分别为 6、4、5、4、3、8；内部状态不计入 |
| 技能图标 | 36 | 每名英雄被动、Q、W、E、R、D 各 1 个 |
| 特效资源 | 按表现层确认 | 不预设一技能一模型；优先复用项目资源 |

推荐批次：

1. 先核对六名英雄的核心特效候选，尤其是冰、刀光、魔法阵、护盾、飞行和花田类资源。
2. 确认特效缺口后，再生成 Buff 图标和技能图标，避免图标颜色与最终特效语言冲突。
3. 用户确认图标和特效后，迁入正式资源目录并登记资源库。
4. 最后创建 20-25 的英雄 Buff 文件、更新聚合入口，再把技能配置引用到正式资源路径。

| 字段 | 要求 |
| --- | --- |
| 资源用途 | 具体到技能、阶段和表现层，例如“椿 W 完美招架命中特效” |
| 候选文件 | 外部绝对路径或项目内路径；确认后再写游戏内路径 |
| 视觉确认 | 主体轮廓、颜色、材质、运动方式和持续方式 |
| 朝向与锚点 | 挂点、世界坐标、目标坐标、目标方向或飞行方向 |
| 生命周期 | 创建点、持续时长、销毁点、打断/死亡收尾 |
| 贴图依赖 | 私有贴图、原生贴图、MDX 内部路径和是否需要迁移 |
| 去重信息 | 完整 SHA-256、字节数和已有相同/相近资源 |
| 适用限制 | 是否需要叠加、是否适合持续层、是否会遮挡、是否只能正面显示 |
| 验收状态 | 待预览、候选、用户确认、已迁入、已登记、已实机验证 |

## 7. Buff 图标生成和接入顺序

### 第一阶段：资源确认

- 先在项目特效库按元素、形态、弹道和护盾分类检索。
- 为六名英雄建立候选特效清单，不把外部资源直接复制进正式导入目录。
- 先确认核心表现：爱蜜莉雅冰晶/冰花、红叶和椿刀光/VF、伊蕾娜扫帚/结界、塞莉亚节点/法阵、芙莉莲 Zoltraak/花田。
- 缺少候选时再生成或迁入，并按资源规则处理私有贴图；Warcraft 原生贴图保持原生路径，不迁移副本。

### 第二阶段：生成图标

- 先生成 30 个 Buff 图标，按英雄分批，每批生成后检查小尺寸识别度、白银外框、透明边缘和同类区分度。
- 再生成 36 个技能图标，保持每名英雄的被动/Q/W/E/R/D 视觉体系。
- 每个图标先保存 1K 源图；用户确认后再生成正式缩放版本和项目需要的贴图格式。
- 图标路径在正式文件落地前统一核对，不在规划阶段填写幻觉路径。

### 第三阶段：Buff 表落地

确认真实效果和图标后，为每个英雄创建单独 Buff 文件：

- `TS/系统/05．Buff系统/03．Buff表/02．英雄/20．爱蜜莉雅.ts`
- `TS/系统/05．Buff系统/03．Buff表/02．英雄/21．朱雀院红叶.ts`
- `TS/系统/05．Buff系统/03．Buff表/02．英雄/22．朱雀院椿.ts`
- `TS/系统/05．Buff系统/03．Buff表/02．英雄/23．伊蕾娜.ts`
- `TS/系统/05．Buff系统/03．Buff表/02．英雄/24．塞莉亚·克莱尔.ts`
- `TS/系统/05．Buff系统/03．Buff表/02．英雄/25．芙莉莲.ts`

并更新 `TS/系统/05．Buff系统/03．Buff表/02．英雄/index.ts` 聚合入口。落地时每个 Buff 必须同步确认 `buffID`、`type`、`maxStack`、刷新规则、驱散规则、tooltip、图标、表现覆盖字段和真实运行逻辑。

### 第四阶段：技能配置接入和实机验收

- 技能配置只引用已确认的游戏内模型路径和图标路径。
- 动作、音效、特效创建点、挂点、缩放、朝向、持续时间和销毁点必须与六份英雄规划一致。
- 重点验收特效是否残留、方向是否错误、持续效果是否超出真实窗口、打断/死亡后是否清理，以及图标与实际状态是否一致。
- 资源导入和 Buff 接入完成后按本次修改的 TS 文件执行局部构建；仅文档或临时资源阶段不运行 TS 构建。

## 8. 当前结论

- 第一批需要规划并最终生成的 Buff 图标为 30 个。
- 第一批需要规划的技能图标为 36 个。
- 特效优先级高于图标：先把六名英雄的核心表现资源找齐，避免生成与实机特效风格冲突的图标。
- 六名英雄的技能特效和普攻弹道候选已分别记录在各自资源文件；模型外观、贴图路径、序列和 SHA-256 详情以各自文件第 4 节为准，后续不再把候选集中追加到本文或全局备忘录。
- 本文完成的是资源拆分和生成顺序，不是 Buff 表接入，也不是技能实现完成。
