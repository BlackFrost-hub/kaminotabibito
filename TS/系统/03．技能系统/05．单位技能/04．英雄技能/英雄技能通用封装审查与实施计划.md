# 英雄技能通用封装审查与实施计划

## 1. 文档目的

本计划用于治理 `TS/系统/03．技能系统/05．单位技能/04．英雄技能` 下的技能实现，目标是让后续英雄制作尽量配置化，优先复用项目已有封装，减少英雄技能文件中的重复实现。

本计划只处理以下两类问题：

1. 英雄技能已经存在可用公共封装，但仍然在技能文件中重复实现。
2. 多个英雄反复出现同一种实现模式，适合沉淀为后续可复用的通用封装。

英雄专属的伤害公式、形态规则、连段表现、目标追踪规则和源 JASS 特殊业务逻辑，不因为代码相似就强行抽象。

当前目录初步统计约 189 个 TS 文件、约 4.1 万行代码。后续模型必须在执行每一批迁移前查看目标文件当前 diff，保留用户已有改动，不做整目录重写。

## 2. 执行前规则

执行任何代码修改前，必须按以下顺序读取：

1. `.cursor/rules/README.md`
2. `.cursor/rules/GLOBAL_AGENT_PROMPT.mdc`
3. 与目标文件对应的子系统规则，至少包括英雄制作规则、技能实现规则和工具补丁安全规则
4. `C:\Users\Administrator\.codex\skills\encoding-patch-safety\SKILL.md`

执行约束：

- 先确认规则、现有封装和目标文件，再动手修改。
- 优先使用 `TS/lib`、技能函数和机制组件中的已有安全封装。
- 不使用 Lua 数学库。三角函数、距离、极坐标等优先使用项目已有封装；没有合适实现时补到公共层。
- JASS 回调使用文件级具名函数，不使用匿名闭包。
- 不混用 `jass`、`BJ`、`japi`。需要兼容 TSTL 时优先使用 `this: void`、本地别名和安全版封装。
- 不为了 TSTL 修改 `fix-lua-for-pack.js`。
- 不主动查看生成 Lua，除非正在检查 TSTL 的 `self/nil` 错位。
- 新建底层 TS 文件顶部统一使用 `@noSelfInFile`；不能随便给已有底层 `lib` 文件增加该标记。
- 调试输出统一使用 `TS/lib/扩展函数/自定义扩展函数/03．调试输出.ts`。
- 使用 `apply_patch` 做局部修改，保持 UTF-8，禁止整文件读写式重写。
- 不擅自打包地图。

## 7. 每批修改的文件边界

每次只修改当前批次涉及的 TS 文件和必要的公共封装文件。

修改普通 TS 后执行：

```powershell
npm run build:files -- "本次修改的TS文件1" "本次修改的TS文件2"
```

参数只能传本次实际修改或新建的 `TS` 目录下 `.ts` 文件，并且每个路径使用双引号。

以下情况才执行完整构建：

- 修改 `TS/global.d.ts`
- 修改 `tsconfig.json`
- 修改公共类型或公共导出签名
- 删除或重命名 TS 文件
- 局部构建无法验证变更
- 最终交付验证

只修改本 Markdown 文档或其他不参与 TSTL 的文档时，不运行 TS 构建。

## 8. 验收标准

静态验收：

- 同语义的单位ID、存活、距离、角度函数不再在英雄层重复实现。
- 没有未解释的 `Math.cos/sin/sqrt/atan2` 等数学库调用。
- JASS 回调均为具名函数。
- 普通范围查询不再重复手写单位组枚举。
- 临时单位有明确创建和清理路径。
- 特效、单位组、计时器和上下文在结束、死亡、超时和中断时均清理。
- 多段技能壳不会错误保留一段、二段或三段技能。
- 技能伤害、治疗、当前生命和最大生命的语义明确。

运行时验收：

- 技能正常释放和结束。
- 技能被打断后可以重新释放。
- 技能窗口超时后阶段正确复位。
- 单位死亡、变身和替换后没有残留上下文。
- 特效不会无限存在或残留旧方向、旧挂点和旧Z高度。
- 联动技能不被通用清理逻辑误删。
- 伤害事件、暴击、技能加成和治疗加成仍按原逻辑工作。

## 9. 交接给其他模型的执行格式

每个模型开始工作前必须报告：

- 已读取的规则文件
- 本批准备修改的文件
- 本批复用的已有封装
- 需要新增的公共封装
- 明确保留的英雄专属逻辑

每批完成后必须报告：

- 实际修改文件
- 删除或替换的重复实现
- 新增的公共接口
- 保留的例外及原因
- 局部构建命令和结果
- 尚未验证的运行时行为

多个模型不得同时修改同一个公共封装文件或同一个英雄技能文件。公共封装必须先完成接口设计和单独构建，再迁移英雄调用方。

本计划文档本身不要求 TS 构建，也不要求地图打包。

## 10. 第一批优先执行的简单任务

本章节专门给能力较弱的执行模型使用。任务必须按小批次执行，每个模型只处理一个明确类别，完成后再交给下一个模型。以下任务不涉及复杂技能业务，不涉及重新设计伤害公式，不涉及多段技能壳，不涉及形态切换和复杂弹道。

### 10.1 执行总原则

- 只做已有封装的调用替换，暂时不新增复杂公共 API。
- 一个任务只修改少量同类文件，禁止一次性重写整个英雄目录。
- 先查看目标文件的当前内容和 git diff，发现用户已有改动时在原有代码上局部修改。
- 每个任务完成后执行一次对应文件的局部构建。
- 如果替换后发现筛选条件、角度单位、生命周期或伤害语义不完全一致，立即停止该文件并记录为复杂任务，不要强行替换。
- 任何涉及 `R技能` 大段状态机、形态切换、复杂弹道、时间停止、生命快照或多段连招的文件，暂时不要交给简单任务模型处理。

### 10.2 优先级一：删除重复的基础几何函数

这是最简单、收益明确的一批任务。只替换函数来源和调用，不改变业务参数。

优先处理：

- [克劳德Q技能.ts](./01．克劳德/02．Q技能.ts)
- [SaberQ技能.ts](./17．Saber/02．Q技能.ts)
- [SaberW技能.ts](./17．Saber/03．W技能.ts)
- [SaberR技能.ts](./17．Saber/05．R技能.ts)
- [佐佐木小次郎Q技能.ts](./11．佐佐木小次郎/01．Q技能.ts)
- [佐佐木小次郎D技能.ts](./11．佐佐木小次郎/04．D技能.ts)
- [铃仙Q技能.ts](./14．铃仙/02．Q技能.ts)
- [黑崎一护Q技能.ts](./14．黑崎一护/02．Q技能.ts)

执行内容：

1. 删除本地的 `两点角度`、`计算两点角度`、`两点距离`。
2. 从 `系统.03．技能系统.00．技能模板+函数.02．通用函数.19．战斗公共工具` 引入对应函数。
3. 保持原来的角度单位、参数顺序和调用顺序。
4. 如果原函数没有归一化角度，而公共函数会归一化角度，必须先确认调用方是否依赖负角度；不能直接替换。

不要在这一批处理技能方向偏移、模型朝向偏移或技能特殊角度算法。

### 10.3 优先级二：删除重复的单位ID和存活判断

优先处理鹿目圆、蕾米莉亚、一方通行、坂井悠二、藤原妹红中的简单重复函数。

重点函数：

- `取单位ID`
- `取单位句柄ID`
- `句柄ID`
- `单位存活`
- 只判断 `unit != null && unit !== 0 && GetUnitState(unit, UNIT_STATE_LIFE) > 0.405` 的本地函数

执行内容：

1. 统一改用战斗公共工具的 `取单位ID` 和 `单位存活`。
2. 如果原函数额外判断 `GetUnitTypeId(unit) !== 0`，先确认公共 `单位存活` 是否已经覆盖该语义。
3. 如果原函数同时要求指定单位类型，保留英雄专属的类型判断，只替换基础存活判断。
4. 删除替换后不再使用的 `GetHandleId`、`GetUnitTypeId` 本地别名。

不要处理带有“形态有效”“特定马甲类型”“技能上下文是否属于当前英雄”判断的复合函数。

### 10.4 优先级三：统一简单的定时点特效

只处理“创建一个点特效，延迟后销毁”这一类直线逻辑。

优先检查：

- 鹿目圆Q/W/E/R中的短时点特效
- 提米诺斯Q/R中的短时点特效
- 云端W中的短时点特效
- 八云紫部分点特效
- Saber部分没有绑定单位的短时特效

优先使用：

- `createTimedEffect`
- `创建点特效`
- `销毁点特效`

不要处理：

- 弹道移动中的特效
- 需要每 Tick 跟随单位的特效
- 需要绑定挂点并替换旧特效的特效
- 需要特殊 Z 高度、旋转矩阵或特效组的表现
- 和单位壳生命周期绑定的特效

验收重点是持续时间、坐标、Z高度和缩放不发生变化。

### 10.5 优先级四：统一简单的临时单位创建

只处理明确属于临时表现单位、创建后由技能自己清理的单位。

优先检查：

- 铃仙D的弹幕单位
- 铃仙E的临时弹幕单位
- 黑崎一护E的视野马甲
- 佐佐木小次郎D的残影和刀光单位
- 坂井悠二Q/D中明确标注为技能马甲的单位

执行内容：

1. 使用 `创建单位并登记排泄安全` 创建单位。
2. 保留原有单位类型、所有者、坐标和面向。
3. 保留原有显式清理逻辑。
4. 不改变单位的生命值、无敌、路径、动画和附加特效配置。

如果该单位参与死亡事件、召唤物管理、单位技能壳监听或长期存活状态，跳过本任务，归入复杂任务。

### 10.6 优先级五：统一简单的范围敌军查询

只处理默认目标规则完全一致的范围查询。

可以直接考虑替换的条件：

- 只需要有效敌军
- 排除自身规则与公共封装一致
- 不需要建筑、古树、机械或无敌单位
- 不需要保留 JASS 单位组句柄
- 不需要在枚举过程中修改原组

优先使用：

- `获取坐标范围敌人`
- `获取单位周围敌人`
- `getEnemyUnitsInRange`

暂时不要改：

- 十六夜咲夜需要精确控制枚举组的技能
- 坂井悠二D需要 `ForGroup` 回调内访问 JASS 枚举单位的逻辑
- 需要同时处理友军和敌军的技能
- 需要特殊建筑、古树或马甲筛选的技能

### 10.7 优先级六：把简单 JASS 回调改成具名函数

只处理回调内容不依赖闭包局部变量，或者可以通过一个简单参数对象传递的情况。

优先处理：

- `addDelayedCallback(100, () => DestroyLightning(...))` 这一类单动作回调
- 单纯调用一个清理函数的延迟回调
- 单纯调用一个状态函数的周期回调
- 不需要访问外层临时变量的 `ForGroup` 回调

执行方式：

1. 新增文件级具名回调函数。
2. 需要参数时定义参数对象并通过计时器变量传入。
3. 回调签名使用 `this: void`。
4. 不把匿名函数移动到另一个匿名包装函数中。

复杂闭包暂时保留并登记，不能为了形式上的“无匿名函数”破坏状态生命周期。

### 10.8 优先级七：替换简单的极坐标三角函数

只处理表达式结构明确的代码：

```ts
x + distance * Math.cos(angle)
y + distance * Math.sin(angle)
```

优先使用：

- `极坐标X`
- `极坐标Y`

或者使用项目已经存在的 JASS `Cos`、`Sin` 安全别名。

优先检查：

- 佐佐木小次郎Q/D
- 坂井悠二D中的马甲偏移
- 八云紫技能中的固定半径偏移
- 云端W中的直线路径推进

不要在这一批修改贝塞尔曲线、曲线弹道、方向插值或带有弧度/角度混合的复杂算法。

### 10.9 优先级八：清理简单的无用 JASS 别名和导入

在完成上述替换后，逐文件清理：

- 不再使用的 `GetHandleId`
- 不再使用的 `GetUnitTypeId`
- 不再使用的 `GetUnitState`
- 不再使用的 `AddSpecialEffect`
- 不再使用的 `DestroyEffect`
- 不再使用的 `CreateGroup`
- 不再使用的 `GroupEnumUnitsInRange`
- 不再使用的 `Math` 相关别名

只删除已经确认没有调用的别名，不做格式化、不改变量命名、不整理无关 import 顺序。

### 10.10 优先级九：给后续复杂任务建立登记项

简单模型遇到以下情况时，不要继续猜测，直接在任务报告中登记：

- 公共封装筛选条件和源技能不一致
- 角度单位可能不同
- 负角度可能有业务意义
- 直接生命值修改可能涉及当前生命/最大生命语义
- 特效持续时间由多个阶段共同控制
- 一个单位同时存在多个技能实例
- 技能有形态切换或单位类型替换
- 需要修改公共导出签名
- 需要扩展二段技能壳为三段技能壳
- 需要改变伤害系统、暴击系统或治疗系统

登记格式：

```text
文件：
函数或代码区域：
发现的问题：
已有封装：
为什么不能简单替换：
建议交给哪个复杂任务：
需要的运行时验证：
```

## 12. 简单任务交付格式

每个模型完成后必须报告：

- 修改的具体文件
