# Boss 技能总复盘

本文提炼本目录各 Boss 历史问题中反复出现的根因。单 Boss 文件保留事故细节和数值事实，`README.md` 保留实现与验收清单；本文只回答四个问题：最容易错在哪里、为什么静态检查没发现、怎样修才不引入新问题、何时才算真正完成。

## 一、总判断

Boss 技能事故很少只是“某个数值写错”。高频问题通常来自以下断层：

1. 需求写的是完整战斗行为，实现只覆盖了某个主动技能。
2. 正式逻辑正确，测试入口改变了目标、阶段、阵营或坐标，导致观察结论失真。
3. 表现、预警、伤害分别计算自己的时间和几何数据，最终看起来像同一个技能，实际不是同一条时间线。
4. 正常结束可以清理，死亡、中断、重测、阶段切换或多实例并存时不能清理。
5. TS 能编译，但 TSTL 生成后的数组、模块导出或实例方法语义已经改变。
6. 技能代码可以释放，但正式启动、AI、阶段、死亡、奖励或地图入口没有接通。

因此，“技能能放出来”只能证明一个局部入口可运行，不能证明 Boss 已完成。

## 二、最高频的事故模式

### 1. 需求语义没有先定死

- 追踪目标、伤害目标、预警目标经常被错误复用。菲尼克斯尔的熔岩吐息只应追踪一个英雄，但伤害必须枚举扇形内全部敌人。
- “锁定目标”可能是锁定单位、锁定坐标、锁定方向或每 Tick 重新读取。里科特投影需要永久绑定各自目标并持续读取目标位置；莫尔特斯腐败之种则在施法开始时锁定落点坐标。
- 阶段机制、被动和场地效果不能伪装成主动技能。测试命令应触发真实入口或准备可观察条件，不能为了命令列表完整制造不存在的技能壳。
- 配置文字不能代替运行时实现。瑟兰迪尔曾存在 Buff 描述已写属性变化，但技能目录没有对应数值回调的情况。

处理原则：实现前先写清目标来源、快照时点、命中集合、阶段来源、触发入口和结束条件；其中任何一项不明确，都不应直接写业务代码。

### 2. 把局部可运行误判为完整战斗

完整链路至少包括：

`单位/物编 -> 启动属性/弱点 -> Boss 启动监听 -> Boss 共享状态/运行时上下文 -> AI/阶段/被动 -> 技能与机制 -> 死亡清理 -> 奖励/固定掉落`

- 影骨莫特斯曾有技能入口和 AI 懒创建上下文，但正式开战没有显式启动监听；死亡结算还用错单位名，固定任务掉落也未接入。
- 亚伦柯斯、米亚、祖地双灵卫曾出现技能链完整，但正式剧情事件、矩形、出生点或玩家入口没有源码事实支撑。
- 安兹存在两种设计模式，但正式工厂一度默认写死其中一种。模式分支存在不等于两种模式都有正式入口。
- 固定弱点数量和额外随机弱点数量是两套语义。额外随机弱点必须排除固定弱点和本轮已抽取结果，候选不足时只创建剩余数量，不能用同一个“弱点数”字段混写。
- `Boss战.单位`、`Boss战.绑定单位` 和 `udg_Boss` 不能视为可互换别名。启动和结束时必须按各消费系统的真实读取入口对称写入、校验和清理；否则复活系统可能取不到当前 Boss，回退到默认复活点。

处理原则：审计必须从开战前一层开始，直到奖励和所有清理结束；固定弱点、额外随机弱点和共享 Boss 句柄分别核对其配置与消费方。找不到剧情事件、矩形变量或坐标时应明确记录缺口，不能用测试坐标或记忆补值。

### 3. 测试环境掩盖了正式行为

- 固定步兵适合测伤害，不适合测追踪、转向、冲锋和动态预警。
- 测试入口显式传入目标时，可能覆盖正式技能的自动选敌；看到技能命中测试靶，不能证明正式选敌正确。
- 测试 Boss 可能属于玩家，提示圈会按友方颜色染色，敌我筛选和原生攻击行为也与正式战斗不同。
- 只改 `context.阶段` 不一定真正进入阶段。里科特、米亚、夏提雅均要求同步动态最大生命、当前生命和真实阶段入口；动态最大生命必须使用项目确认的 JAPI 读取。
- 正式坐标直接用于测试场会把机制生成到镜头外。测试只能通过上下文覆盖或平移副本改坐标，不能改写正式配置对象。
- 预置英雄被移动和选中，不代表它已经经过玩家英雄登记链；依赖英雄注册的系统仍可能拒绝它。

处理原则：每条测试命令必须说明它准备了什么状态、调用哪个正式入口、预期观察什么差异。阶段命令若没有触发阶段独有后续事件，就不能证明阶段强化生效。

### 4. 时间线只有动作，没有真实控制和生效时点

- 调度器“忙碌”只会阻止下一次选技能，不会阻止 Boss 移动。夏提雅多个技能因此需要真实硬直，而不是只设置忙碌时间。
- 动作、硬直、吟唱、预警和伤害必须共享明确的时间线；读条开始不等于效果已经生效。
- 前摇、位移和持续状态是不同控制阶段。前摇由施法时间线控制，冲锋/跳跃开始后由位移系统接管，持续状态另用独立通道表示。
- 自身施法硬直不能被识别成外部硬控。夏提雅曾因 Buff 分类错误，在蓄力结束时把自己的硬直判成打断条件。
- 专属机制不能机械套普通时间线。根系觉醒、触手解放等包含隐藏、暂停、限时目标组和成功/失败分支，应保留专属状态机。

处理原则：先画出“开始、预警、生效、持续、结束”五个时点，再决定公共时间线负责哪些部分；公共层只管理通用控制，业务分支留在 Boss 层。

### 5. 预警、表现和结算没有复用同一份几何

- 矩形提示接口接收路径起点，底层会自行前移到模型中点。巴尔扎罗斯和莫尔特斯都曾因调用方先传中点而再次偏移半段。
- 预警半径必须覆盖真实命中外沿。树魔扩散冲击波的中心射程加弹幕命中半径，才是完整危险范围。
- 表现创建点、模型主轴和伤害线段必须一起核对。里科特射线模型沿负 Y 轴延伸，不能只按常规模型朝向推断。
- 随机落点、目标坐标和方向必须只抽取或快照一次，再同时供预警、表现与结算使用。

处理原则：每次释放先生成一份技能几何数据，后续所有层只读取它；除明确设计为追踪外，不允许各层重新选点或重新算方向。

### 6. 把点特效当成弹体，把轨迹数据当成飞行成功

- 菲尼克斯尔曾用落点点特效代替炽羽和骸骨弹幕，配置中的数量、速度和飞行过程实际都未生效。
- XYZ 轨迹有 Z 值，不代表单位马甲支持飞行高度。还必须检查载体物编和每 Tick 的高度写入。
- 改向弹幕只更新方向，不会自动开启新的命中段。里科特返程需要显式重置命中记录，同时保证累计距离覆盖两程。
- 纯视觉弹道应优先使用特效载体；需要被攻击、反弹或拦截时才使用单位载体，并明确路径、碰撞、命中次数和销毁规则。

处理原则：弹幕验收必须逐项检查载体、数量、速度、起终点、Z、朝向、命中记录、到达回调、命中特效和销毁，不能只看最终落点。

### 7. 伤害链路语义错位

- 项目技能伤害统一使用 `ATTACK_TYPE_NORMAL`；火、冰、毒、暗、魔法等分类由 `DAMAGE_TYPE_*` 决定。多个 Boss 都曾把 `ATTACK_TYPE_MAGIC` 当作魔法分类。
- 动态公式与预计算快照不能混用。每 Tick 读取攻击力、施法时快照攻击力、结算时读取目标最大生命，是三种不同语义。
- 普攻基础修正不能改成额外提交一次技能伤害，否则会重复触发伤害事件和后续修正。
- 真正改变原生伤害类型时，只改 TS 快照不够；需要归零原事件并按真实类型重提交，同时阻止递归转换。
- 承伤转移必须携带 `isDamageTransfer` 等元数据，条件修正明确排除转移事件，避免再次分担或重复减伤。
- 护盾属性匹配必须先读底层语义。巴尔扎罗斯火护盾曾因只吸收同属性伤害，导致冰霜“1.5 倍破盾”永远进不了护盾结算。

处理原则：任何伤害修改都要明确它位于“公式、基础伤害修正、类型转换、护盾、最终伤害”中的哪一层；不知道所在层级时，不得直接追加伤害。

### 8. 生命周期只处理了正常结束

- 延迟、周期、弹幕、特效、召唤物、机制单位、护卫、吟唱条和临时属性都必须登记到同一战斗上下文或机制实例。
- 结束原因至少区分：被击杀、自然到期、主动销毁、机制清理、单位失效、技能中断、阶段切换和战斗结束。米亚核心/分身、卡瑟拉触手组的成功与超时结算都依赖这一区分。
- 持续区域的首次扫描可能只建立在场列表，不触发 `on进入`。巴尔扎罗斯熔岩喷发把穿越事件当作一次性爆发枚举，导致创建时已在圈内的玩家漏伤害。
- 多实例周期不能每个回调再扫描全局实例表，否则实例数与回调数相乘。影骨幽影爆发曾因此重复推进召唤。
- 分批召唤组必须在最后一批登记完成后再封闭，不能在生成途中因前几批死亡提前判定全灭。
- 死亡自动清理与业务死亡回调不能重复注册；需要死亡后延迟剧情或联合 Boss 收束的场景，则不能机械迁移为立即自动清理。

处理原则：创建机制时同步写退出矩阵；每种退出原因说明“清什么、结算什么、禁止触发什么”。没有退出矩阵的机制视为未完成。

### 9. 公共化不能机械替换

- 公共伤害执行器适合统一公式与元数据，不应吞掉技能专属命中表、状态消费、反击、掉落和阶段分支。
- 公共周期执行器适合固定间隔、固定次数、可提前停止的实例行为；涉及目标切换、接触累计、重组或多阶段状态的周期应保留业务状态机。
- 全局条件伤害规则应注册一次，不应绑定单个 Boss 上下文后随某一实例清理，否则多实例会互相注销规则。
- 公共组件的首次扫描、方法 `self`、结束回调和销毁顺序必须先读实现，不能只凭函数名猜语义。

处理原则：迁移前列出必须保持不变的状态、时点、次数、元数据和退出分支；迁移后逐项对照，而不是只以“代码更短”作为完成标准。

### 10. TSTL 与模块边界错误常被误判成业务 Bug

- 新增模块导出后只构建调用方，运行时会加载旧导出模块并得到 `nil`。影骨阴影穿梭的问题不是 `self` 错位，而是局部构建漏了导出方。
- `any` 会让 `.length` 原样变成 Lua 字段访问，最终得到 `nil`；Lua table 也没有 JavaScript 的 `.slice()`。
- `any` 上的 `.push()` 和实例方法调用可能生成错误的冒号调用；跨模块对象应有明确结构类型，实例方法不得错误声明 `this: void`。
- 普通版封装没有 `@noSelfInFile` 兼容时，应使用安全版、`this: void` 的本地具名包装或局部别名，不应给底层文件随意加 `@noSelfInFile`。
- 生成 Lua 只在排查 TSTL 的 `self/nil` 错位时检查；其他问题不主动查看生成 Lua。修复必须回到 TS 源码，禁止修改 `fix-lua-for-pack.js`。

处理原则：运行时 `nil` 先区分“导出不存在、数组语义错误、方法 self 错位、业务值为空”四类，再决定是否检查 Lua，不能见到 `nil` 就直接加 `@noSelfInFile`。

### 11. 配置、物编和资源不能凭名字猜

- 实际创建 rawcode、父物编 rawcode 和类型表登记必须一致。继承同一父物编不代表运行时 ID 相同。
- rawcode 跨对象类型复用会直接导致 ObjEditing 类型冲突。影骨宝箱 `B00Z` 与 Buff 冲突后，最终统一改用自定义可破坏物 `BZX4`。
- 模型扩展名、内部贴图路径、共享贴图、导入表和运行时物编表必须一起迁移。
- 贴图工具能回读 Alpha 不代表 Warcraft 1.27 能正确显示。安兹黑底问题最终同时涉及 MDX 材质和 BLP 编码格式。
- Buff 图标、模型动作编号、单位名、装备属性键和地图变量都必须从项目事实读取，不能按命名习惯推测。

处理原则：资源或物编问题至少核对“定义、实际创建、运行时识别、导入、实机显示”五层；其中任一层未确认，都不能宣称完成。

### 12. 玩家说明必须来自运行时事实

- “高额伤害”“大幅减速”“短暂控制”无法支持玩家决策。说明应给出前摇、范围、持续、层数、倍率、解除方式和规避动作。
- Buff 注册只保证图标和记录，不保证 tooltip 中描述的属性已经生效；必须反查数值回调、临时属性或伤害修正入口。
- 原生控制与自定义 Buff 是两套生命周期。需要同时显示控制和图标时，必须显式同步。
- 百分比必须说明是固定值追加、基础值比例、总倍率还是当前值快照，避免“提高 30%”产生多种解释。

处理原则：先核对运行时，再写说明；不能用说明文案反推技能已经实现。

## 三、最有价值的反例

| 反例 | 暴露的问题 | 应记住的结论 |
| --- | --- | --- |
| 夏提雅 `.slice()` | TS 写法合法，Lua table 无该方法 | 跨 TSTL 的数组操作必须使用明确类型和项目兼容写法 |
| 影骨公共工具导出为 `nil` | 局部构建漏掉本次已修改的导出方 | 局部构建只传本次修改文件；公共导出签名变化执行完整构建 |
| 巴尔扎罗斯熔岩喷发漏首批目标 | `on进入` 被误当爆发枚举 | 先读公共区域首次扫描语义，不改底层迁就单技能 |
| 菲尼克斯尔熔岩吐息 | 追踪集合被当伤害集合 | 追踪对象和命中对象必须分开定义 |
| 里科特返程弹幕不再命中 | 改方向未重置命中段 | 轨迹状态和命中状态是两套状态 |
| 莫尔特斯测试场机制在镜头外 | 只移动 Boss，未平移场地配置 | 测试坐标用上下文副本映射，不能污染正式配置 |
| 影骨幽影多实例重复召唤 | 每实例回调又扫描全局实例 | 周期回调只推进自己的变量实例 |
| 安兹贴图黑底 | 工具回读 Alpha 正常，旧版客户端仍不兼容 | 资源验收必须包含目标 Warcraft 版本实机 |
| 影骨宝箱 `B00Z` 冲突 | rawcode 被不同对象类型复用 | 新物编 ID 必须先查全项目占用和对象类型 |
| 巴尔扎罗斯运行时重复写自导 | 固定物编属性又被 JAPI 重写 | 固定属性留在物编，同值运行时写入也可能有风险 |

## 四、固定审计顺序

以后检查或新增 Boss，按以下顺序进行；后一步不能替代前一步：

1. 读设计、Boss 配置、Buff 表和对应复盘，列出技能语义与阶段表。
2. 查公共封装，确认目标选择、时间线、伤害、提示圈、弹幕、机制单位、周期和清理的真实语义。
3. 核对正式链路：启动属性、启动监听、上下文、AI、阶段、被动、护卫、死亡、奖励、固定掉落和场景入口。
4. 为每个技能写时间线、几何快照、伤害层级和退出矩阵。
5. 核对测试入口是否改变目标、阵营、生命来源、坐标、英雄登记或自动施法开关。
6. 修改 TS 后优先局部构建，参数只传本次修改或新建的 TS 文件；修改公共类型或导出签名、删除/重命名 TS 文件、局部构建失败或最终交付验证时执行完整构建。
7. 仅在排查 TSTL 的 `self/nil` 错位时检查对应 Lua，不通过修改生成物或打包脚本修问题。
8. 实机按 P1/P2/P3、普通/英雄/移动目标、正常结束/中断/死亡/重测、多实例重叠分别验证。
9. 删除阶段性调试日志，回填单 Boss 复盘；只有静态链路、构建和实机结论都标明状态后才交付。

## 五、完成标准

以下任一情况存在，都不能写“已修复完成”：

- 只通过 TypeScript 编译，没有对应实机验证。
- 只在测试命令成功，正式启动监听或 AI 没有接通。
- 只验证 P1，没有触发 P2/P3 的真实差异。
- 只看特效，没有核对伤害次数、Buff 层数、控制次数和目标集合。
- 只验证正常结束，没有验证死亡、中断、清理和重复测试。
- 地图事件、矩形、坐标、物编或资源仍靠占位值或猜测。
- 调试日志仍残留，或生成 Lua 被手工修改。
