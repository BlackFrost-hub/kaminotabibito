# Boss自动通魔AI规划

这份文档现在不再是假设“从零开始做 Boss AI”，而是基于当前已经存在的桥接壳子继续往下推进。

当前已经落地：

- `03．Boss战启动桥接`
  - 能监听旧 JASS 发出的 `Boss战启动` STES 事件
  - 能优先读取 STES 里的 `Boss`
  - 如果没有，会延迟一帧补读：
    - `YDUserData("Boss战", "单位")`
    - `YDUserData("Boss战", "绑定单位")`
  - 读到 Boss 后，登记到本地 Boss 自动技能注册表

当前还没落地：

- Boss 主动扫描施法运行时
- Boss 技能扫描与缓存
- 仇恨目标选择
- 主动施法执行
- Boss 战结束后的注销/清理

## 一、目标

为重要 Boss 提供一套“战斗开始后，自动主动施法”的运行时。

第一阶段目标保持简单：

- 只服务 Boss
- 只做主动扫描施法
- 不和 `01．受击反应施法` 混在一起
- 先支持通魔技能和少量原生模板技能
- 先以“稳定能跑”为主，不追求复杂权重和阶段脚本

## 二、和受击反应施法的边界

`部分AI放技能.j` 迁到的 `01．受击反应施法`，语义是：

- 玩家英雄打到怪
- 怪在受伤后立刻反制放技能

Boss 自动通魔 AI 的语义不同：

- Boss 战已经开始
- Boss 周期扫描自己当前可用技能
- 主动找目标、判断距离、判断蓝量和冷却
- 然后主动下单施法

所以后续目录建议是：

- `01．受击反应施法`
- `02．Boss主动扫描施法`
- `03．Boss战启动桥接`

`09` 负责把旧 JASS 的 Boss 战启动上下文桥接到 TS。
`02` 负责真正的 Boss 主动施法本体。

## 三、建议目录

后续新增：

```text
TS/系统/03．技能系统/06．AI自动使用技能/
├─ 02．Boss主动扫描施法/
│  ├─ 00．常量定义.ts
│  ├─ 01．技能扫描.ts
│  ├─ 02．目标选择.ts
│  ├─ 03．施法执行.ts
│  ├─ 04．运行时注册表.ts
│  ├─ 05．周期驱动.ts
│  └─ index.ts
```

这样分的原因：

- `技能扫描` 和 `施法执行` 可以单独自检 Lua 形态
- `运行时注册表` 负责 Boss 生命周期，不和扫描逻辑缠死
- `周期驱动` 只关心 tick，不关心技能细节

## 四、启动方式

Boss 主动施法不建议像小怪那样全局挂一个大扫描。

推荐方式：

1. 旧 JASS / 过渡层触发 `Boss战启动`
2. `03．Boss战启动桥接` 读到 Boss
3. 把 Boss 登记到本地注册表
4. `02．Boss主动扫描施法` 开始对这只 Boss 进行周期驱动

以后完整迁移 Boss 战后，目标变成：

- 直接由 TS 的 Boss 战流程自己调用注册
- 不再依赖 STES

## 五、Boss 来源读取规则

这是当前已经确定的兼容规则，后续不要改乱：

1. 先读 STES 里的 `Boss`
2. 如果没有，就延迟一帧
3. 延迟后按顺序补读：
   - `YDUserData("Boss战", "单位")`
   - `YDUserData("Boss战", "绑定单位")`
4. 三处都没有：
   - 说明旧 JASS 的 Boss 战启动上下文有问题
   - 直接 `debug` 并跳过

这个规则是迁移期兼容旧主线 / 旧 Boss 战触发的重要前置。

## 六、技能扫描策略

第一版建议直接扫描 Boss 自身技能栏，不先做人肉大配置表。

优先可用 API：

- `EXGetUnitAbilityByIndex`
- `EXGetAbilityId`
- `DzGetUnitAbilityOrderId`
- `DzGetUnitAbilityRange`
- `DzGetUnitAbilityCost`
- `DzGetUnitAbilityCool`
- `DzGetUnitAbilityDataB`

扫描结果缓存为“可施法技能描述”，避免每个 tick 全量重扫。

建议缓存字段：

- `abilityId`
- `orderId`
- `range`
- `cost`
- `cool`
- `dataB`
- `目标类型`
- `是否模板技能`

缓存刷新时机建议：

- Boss 首次注册时扫一次
- 明确需要时手动刷新
- 不在每个 tick 重扫

## 七、目标类型

第一版先支持这几种：

- 无目标
- 自身
- 单位目标
- 点目标
- 单位或点目标

对于通魔技能，先用 `DataB` 做粗分类。
对于少量已知模板技能，可以单独做模板识别兜底。

## 八、目标选择

第一版只做最简单、最稳定的目标来源：

- 最高仇恨目标

后面再扩展：

- 最近玩家
- 随机玩家
- 低血量玩家
- 指定区域目标点

## 九、施法过滤

第一版候选技能过滤建议只做这些硬条件：

- Boss 活着
- 技能等级 > 0
- `orderId != 0`
- 技能不在冷却
- 蓝量足够
- 目标有效
- 距离够

不要第一版就塞：

- 复杂权重
- 多阶段切换
- 花哨概率表
- 战斗脚本语言

## 十、运行时注册表

运行时注册表应至少记录：

- Boss 句柄
- Boss handleId
- 是否已注册
- 下次允许施法时间
- 扫描缓存
- 启动来源
  - `STES.Boss`
  - `Boss战.单位`
  - `Boss战.绑定单位`

这样后面调试时能直接看出：

- 这只 Boss 是从哪条旧链路进来的
- 是不是重复注册
- 有没有只启动了桥接但没进入主动施法

## 十一、周期驱动

第一版推荐：

- 中心计时器统一 tick
- 间隔保守一些，例如 `300ms ~ 1000ms`
- 每次遍历已注册 Boss
- 只处理有效且活着的 Boss

不建议：

- 每只 Boss 各起一个原生 timer
- Boss 很多时频繁全量扫技能

## 十二、后续接线顺序

建议按这个顺序继续做：

1. 在 `02．Boss主动扫描施法` 建运行时注册表
2. 让 `03．Boss战启动桥接` 在登记壳子后，同时调用“注册主动施法 Boss”
3. 先做最简单的：
   - 最高仇恨目标
   - 技能扫描缓存
   - 单位 / 点 / 无目标三类施法
4. 能稳定跑通一只 Boss 后，再补模板识别和 override

## 十三、迁移期说明

迁移期的原则是：

- STES 只负责告诉 Lua “Boss 战开始了，而且这只 Boss 是谁”
- 核心逻辑写在 TS
- 不继续在 JASS 那边追加新 AI 逻辑

也就是说，后续如果要补参数，例如：

- 哪个区域的 Boss 战
- 由哪个玩家触发
- Boss 战阶段号

也应该是：

- STES 传上下文
- TS 解释上下文
- TS 控制行为

## 十四、当前结论

现在这个规划不是空文档了，实际起点已经明确：

- `Boss战启动桥接` 已经存在
- 下一步不需要再纠结“Boss 怎么启动”
- 直接开始做 `02．Boss主动扫描施法` 即可

当前最重要的工程边界是：

- 小怪受击反应，继续走 `01．受击反应施法`
- Boss 主动自动施法，单独做 `02．Boss主动扫描施法`
- 两类不要混
