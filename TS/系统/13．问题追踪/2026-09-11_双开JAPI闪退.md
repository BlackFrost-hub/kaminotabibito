# 双开时 JAPI 闪退排查

## 现象

- 单独启动一个 Warcraft 3 客户端通常可以进入。
- 本地同时启动两个客户端时，曾出现加载卡住、闪退或 Windows “内存不能为 written”错误。
- 曾出现：`Call jass function crash.<unknown>`。
- 目前恢复旧 JASS 触发器后，双开也可以进入，暂未稳定复现。

## 关键证据

Lua traceback 曾定位到：

```text
主线任务 -> 主线引导UI -> 02．主线引导框架.lua -> DzCreateFrameByTagName
```

另一次 JASS 调试窗口定位到旧 GUI 触发器“背景框UI基础”的 `DzCreateFrameByTagName`。

## 已做隔离测试

1. 主线剧情系统改为分段加载，并加入 `debug.traceback` 诊断。
2. 主线引导 UI 曾改为唯一帧名，并延迟初始化；之后临时禁用。
3. 旧“背景框UI基础”触发器曾保持关闭；恢复后目前仍可进入。
4. 临时禁用整个 `main.lua` 系统入口后可以进入。
5. 恢复核心及 01–07 系统后可以进入。
6. 恢复 08 任务系统时曾复现闪退，但后续只开启配置表和运行时核心时可以进入，任务 UI 之后也可以进入。

## 当前状态

- 目前没有稳定证据证明某个单独系统必然导致闪退。
- 更可能是 JAPI Frame 创建时序、旧 JASS 与 TS UI 的交互，或偶发的双客户端启动状态。
- `debug.traceback` 能定位 Lua 调用链，但不能拦截 JAPI 进程级内存崩溃。

## 新确认：任务 UI 触发双开异步掉线

- 关闭 `ENABLE_QUEST_UI_MODULE` 后双开可进入；开启任务 UI 后再次出现异常。
- 任务 UI 为多个玩家槽位预创建帧，其中主面板、列表容器和滚动条 FDF 创建此前未统一传入槽位 `contextId`。
- 已修复这些创建调用的上下文传递，并为动态滚动条帧补齐槽位 ID，避免不同槽位复用同一 FDF 上下文。

## 后续记录要求

- 每次测试注明：旧 JASS 触发器是否开启、Run Map 是否重新打包、双开顺序和两端最后日志。
- 只有连续复现并完成反向验证后，才把某模块标记为根因。

## 新问题：20–25号英雄选择后的双开异步

### 现象

- 单人选择通常正常；双人选择20–25号TS新英雄时曾立即异步或掉线。
- 主要测试英雄为爱蜜莉雅、塞莉亚。
- 老JASS迁移英雄未出现同样稳定的现象。

### 已确认结论

- `GetHandleId`作为配置表键会异步。
- 字符串拼接键（单位类型ID+玩家ID）也会异步。
- 固定数字键和固定配置值正常。
- 在英雄注册回调中通过单位调用`GetUnitTypeId`生成登记键属于高风险。
- `YDUserDataSetSafe`单位映射写入会重新触发异步，已撤除。
- 当前登记使用英雄注册回调传入的固定业务ID，不再现场反查单位生成键。
- 20–25动态技能配置按“英雄业务ID → 技能ID → 完整说明”隔离；老英雄没有对应配置时继续读取原生说明。

### 当前规则

- 本地UI链不得调用`DzSetUnitAbilityUpdate`。
- 动态文本本地刷新只负责读取和显示。
- `DzSetUnitAbilityUpdate`只能放在同步技能学习事件中。
- 后续测试必须重新Run Map打包，双开并记录两端最后日志。

## 重大发现（2026-09-12）：阶段4 属架构性违规 —— 本地注册回调修改共享状态

**结论（用户指出 + 代码验证）**：任务UI 是 N 槽设计（各端对称全局创建帧、只做本地显隐），**逻辑状态必须在所有客户端对称修改**；但阶段4 的滚轮/滑块拖拽是 `sync=false` 纯本地注册，回调里**直接修改了参与跨端逻辑解析的状态** → 各端分叉 → 异步/掉线。

### 证据链

1. **本地回调改共享状态**：`09．任务UI滚动与滚轮` 的三个本地回调（`onGlobalThumbLeftPress/Release/DragMove`、`onMouseWheelEvent`）最终都调用 `onThumbDragMove` / `onThumbDragEnd` / `onScrollBarTrackClick`，其中执行 `dragCtx.setCurrentPage(targetPage)` → `TaskUI.listSetCurrentPage` → `this.currentPage = page`。
2. **`currentPage` 参与跨端逻辑解析**：行点击回调用 `rowIndex` 在当前页里解析 `questId`（`toggleExpandForVisibleRow`：`page.questIds[rowIndex]`）。各端 `currentPage` 不一致时，同一个 `rowIndex` 会解析出**不同的 questId** → 后续 `expandedQuestId`（共享状态）被写成分叉值 → 异步。
3. **作者注释已暗示该风险**：`11．任务UI管理器` `applyScrollPageChanged` 上方注释："滚轮/拖拽走 sync=false，本地翻页不能清共享展开态；否则后续 sync=true 行点击读取 oldExpanded 时，各端会出现状态分叉。" —— 只是规避了"清展开态"，没有解决 `rowIndex → questId` 解析分叉。
4. **与二分结果完全吻合**：STAGE=2/3 不崩（未注册这些回调），阶段4 才注册 → 与"本地回调改状态"的触发点一致；"偶发后必现"也吻合（状态一旦分叉不会自愈）；"任务UI 关闭一定不崩"吻合（不注册即不分叉）。
5. **正确范式就在同项目里**：热键走 `registerKeyUpSync` = 本地监听 → `DzSyncData` 广播 → 全房 `onSyncKeyUpData` 对称执行（`DzGetTriggerSyncPlayer()` 取触发玩家）→ `TaskUI.switchCategorySync/togglePanelSync` 里"全局状态全端修改、UI 只对按键者显示"。滚轮/拖拽**缺失这一层广播**。

### 修法方向（待定，二选一或组合）

- **方向A（推荐，贴合现有范式）**：把"翻页结果"同步化。滚轮（离散事件）在本地回调里不直接改状态，改为 `DzSyncData` 广播目标页 → 全房对称执行 `setCurrentPage` + 各自本地显隐；拖拽则**拖动过程只做本地视觉跟手**（`setTaskScrollThumbByRatio`），**松手时广播一次最终页**（避免 mousemove 高频广播）。
- **方向B（更彻底）**：让 `currentPage` 成为**纯本地状态**，同时把行点击从"传 `rowIndex`"改为"直接传 `questId`"（行帧构建时已知），使跨端逻辑不再依赖各端 currentPage；这样本地注册名正言顺。
- 无论哪条，`setCurrentPage`/`onPageChanged` 这条链是否触碰共享状态都要重新过一遍（含 `switchPageLocal` 与 `expandedQuestId` 的交互）。

### 广播内容约定（2026-09-12 确认，实施依据）

- **广播的不是原始输入，而是本地判定后的业务结果**：滚轮/拖拽本地判定命中后，只算出**目标页码（一个整数）**并 `DzSyncData` 广播。**不广播鼠标焦点帧、不广播滚轮增量、不广播鼠标坐标**——原始输入跨端无意义（其他端的鼠标状态与触发者无关）。
- 与热键完全对称：`registerKeyUpSync` 广播的是 `I2S(keyCode)`（**过滤聊天框后的有效键码**），而不是"聊天框是否打开"；滚轮广播的是"翻到第 N 页"，而不是"鼠标悬停在哪个帧上"。
- 拖拽：拖动过程中鼠标位置是高频连续输入，**绝不广播**（滑块跟手为纯本地视觉）；**松手时广播一次最终页**（每次拖拽仅 1 次同步数据）。
- 其他端收到后直接 `setCurrentPage(目标页)`：currentPage 同步后各端页数/页序一致，结果必然一致；只有"切换显示"才走本地分支（与 `switchCategorySync` 同构）。
- 该约定同时说明：**不存在 mousemove 高频广播的性能问题**（因为根本不广播过程）。

#### 2026-09-12 阶段4 代码侦查结论（未测先查）

- `09．任务UI滚动与滚轮.registerTaskUIListWheel` 在 STAGE>=4 时会做两件事：
  1. `ensureTaskThumbGlobalMouseRegistered()` —— 注册**全局**鼠标事件：左键按下(1,1)、左键释放(1,0)、**全局 mousemove**（`DzTriggerRegisterMouseMoveEventByCode`）。⚠️ 该调用位于 `ENABLE_MOUSE_WHEEL_SCROLL` 检查**之前**，即不受滚轮开关控制。

- ⚠️ **注意：本段是"侦查结论"，不是"已修复"**。`sync=false` 的注册方式**未做任何改动**（保持二分对照组干净）：
  - `sync=false` → `runFalseLocalRegistration` 是 lib 的**正式契约路径**（`03．鼠标函数` 注释原文要求"必须经 runFalseLocalRegistration"），项目其他模块也在用，本身不等于 bug；
  - 在未确认阶段4是根因前改动它，会污染对照组（之后崩了也无法判断是原问题还是新改动）；
  - 已修的唯一一处是"拖拽注册不受滚轮开关控制"的开关漏洞（行为不变，只是让开关能拦住它）。
  - 若确认阶段4是根因，候选修法：① 注册去重/幂等化（当前每槽位各注册一次）；② 调用处补 `playerId` 明确注册归属（当前 `ctx.registerMouseWheel(false, cb)` 未传第三参）；③ 延迟注册到面板首次打开时；④ 评估改同步注册的语义代价。

#### 2026-09-12 第3轮：STAGE=4 → **复现！阶段4命中**

- 配置：`ENABLE_QUEST_UI_MODULE = true` + `QUEST_UI_INIT_STAGE = 4`。
- 结果：**双开游戏加载进不去**（问题A 复现）。
- **实测现象细节（用户补充，重要）**：
  - **一端进得去，另一端进不去**（不是两端对称崩溃）。
  - 进不去的那端**卡住**，点击窗口后变**未响应**（进程未退出，主线程阻塞）。
- 结论：崩点确定在**阶段4**（滚轮/滑块全局鼠标注册）。STAGE 2/3 通过、4 挂 → 阶段4 的两块注册即问题A 的根因范围；且与问题B（本地链改共享状态）**同处一地**。
- 关键推论：
  - "单端卡死/未响应"（而非闪退）= **主线程在等待某个永不满足的条件** → 典型"两端执行不对称、某端在等同步"的表现。
  - 这与 **`sync=false` 本地注册在双开下的行为**高度吻合：`runFalseLocalRegistration` 用 `GetLocalPlayer()` 判定，双开时两端各自认为自己是"本地玩家"，注册结果/时序不对称 → 一端在后续同步点（加载期）被卡住。
  - 即崩点**不是"注册了钩子"这件事，而是"用本地注册方式注册"** → 修复方向锁定为**改注册方式（同步注册）+ 回调内本地判定后广播结果**（与问题B 的修法正好组合成一套）。

#### 2026-09-12：滚轮仅玩家1生效 —— 根因与修复

- 现象：任务面板的轨道点击和滑块拖拽正常，但滚轮只有玩家1（主机/槽位0）有效，其他玩家打开自己的任务面板后滚轮无反应。
- 关键结构：`initTaskUIForActivePlayers()` 会在**每个客户端**为所有正在游戏的玩家槽位创建 `TaskUI`。因此，同一个客户端内会依次执行槽位0、槽位1、槽位2……的初始化。
- 原错误链路：
  1. `registerTaskUIListWheel()` 使用模块级 `taskGlobalWheelRegistered`，滚轮只允许注册一次。
  2. 第一个初始化的槽位0调用 `registerMouseWheel(false, onMouseWheelEvent, ctx.playerId)`，把本地滚轮注册绑定到 `playerId=0`。
  3. 槽位1及后续槽位看到全局标记已经为 `true`，不会再次注册。
  4. 结果是滚轮事件只为槽位0注册，玩家1以外的槽位没有自己的本地滚轮事件。
- 修复：滚轮注册仍然保持“每个客户端只注册一次”，但不再传入槽位玩家 ID：
  `registerMouseWheel(false, onMouseWheelEvent)`。
  `sync=false` 仍由硬件输入封装通过 `runFalseLocalRegistration` 在本机注册，不广播硬件事件。
- 回调路由：`onMouseWheelEvent()` 通过 `findVisibleWheelCtx()` 查找“属于本地玩家且当前可见”的任务 UI，再读取该槽位的页数、当前页和滚轮方向。这样一套本地事件可以服务本客户端的本地玩家，不会固定到槽位0。
- 这次问题的通用经验：
  - **模块级只注册一次的本地硬件事件，不能把第一次遍历到的玩家槽位 ID 当作注册过滤条件。**
  - N 槽 UI 的“槽位归属”应由回调路由解决；硬件事件本身应按客户端注册。
  - `sync=false` 的本地注册与“指定哪个玩家槽位接收”是两件事，不能混用。
  - 排查类似问题时，先检查：注册是否只执行一次、是否携带了首次槽位参数、后续槽位是否因全局标记跳过，再检查回调是否能找到本地可见上下文。
- 当前测试控制：假任务入口保持现状，暂不恢复测试数据；先验证玩家1、玩家2分别打开任务面板后的滚轮翻页。
- 修改文件：`02．任务UI拆分/09．任务UI滚动与滚轮.ts`。构建后必须检查生成 Lua，确认调用为 `registerMouseWheel(false, onMouseWheelEvent)`，没有第三个 `playerId` 参数。
