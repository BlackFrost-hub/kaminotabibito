# 支线任务链式子任务改造实施计划

## 1. 背景

当前任务系统的数据与 UI 模型，本质上都是：

- 一个 `QuestData`
- 一组 `objectives`
- 在任务 UI 中渲染为“一条任务行”
- 点击后展开该任务的详情文本、目标、奖励、接受者、完成者

这套模型可以表达：

- 单任务多目标
- 主线 / 支线 / 日常三大分类
- 单条任务的展开查看

但它**不能表达**这次需要的新语义：

- 一个“一级支线任务”本身作为总标题存在
- 这个一级支线任务内部，顺序推进多个“二级流程任务标签”
- 每个二级流程任务标签都像独立任务一样：
  - 有标题
  - 可点击展开详情
  - 有自己的描述 / 奖励 / 地点 / 接受者 / 完成者
- 但这些二级标签又不是普通平级支线任务，而是属于同一个一级支线任务链

所以这次不能只改 UI 文案，必须同时改：

1. 任务数据模型
2. 任务推进逻辑
3. 任务 UI 列表渲染结构

---

## 2. 改造目标

新增一种“链式支线任务”能力，支持：

### 2.1 一级任务

例如：

- `剿灭哥布林洞窟`

它作为**一级支线任务标题**存在于支线任务列表中。

### 2.2 二级流程任务

一级任务内部有 N 个顺序流程节点，例如：

1. 击杀 20 只哥布林
2. 击杀哥布林法师 ×20
3. 击杀哥布林精英 ×3
4. 击杀哥布林大祭司
5. 击杀哥布林王

要求：

- 同一时刻只激活当前流程节点
- 当前节点完成后，自动发布下一个节点
- 最后一个节点完成后，一级支线任务整体完成

### 2.3 UI 表现

一级支线任务在任务列表中作为主容器显示，其下出现二级流程标签列表。

二级流程标签要求：

- 可以被点击展开
- 展开后显示详情区：
  - 任务描述
  - 发布任务的 NPC
  - 任务奖励
  - 任务地点
  - 接受任务的玩家
  - 完成任务的玩家
- 不显示类似现有主任务行的头像图标
- 只保留魔兽原生 UI 背景 / 边框线条风格

### 2.4 兼容性目标

必须保证：

- 现有主线任务逻辑不回退
- 现有普通支线任务逻辑不回退
- 现有日常 / 小任务逻辑不回退
- 不把所有任务都强行改成链式结构

链式子任务能力应当是：

- 对普通任务完全可选
- 只对配置中显式声明的一级支线任务生效

## 3. 设计原则

### 3.1 不伪装成 objectives

不要把“二级流程任务”伪装成一级任务的 `objectives`。

原因：

- `objectives` 只适合表达“同一条任务的内部目标进度”
- 当前 UI 的 `objectives` 是展开后的一组说明项，不是“可点击的二级任务标签”
- 如果硬塞进 `objectives`，会把：
  - 推进语义
  - 领取 / 完成语义
  - 展开查看语义
  全部搅在一起

因此：

- **二级流程任务 = 独立的任务节点数据**
- **一级支线任务 = 任务链容器**

### 3.2 一级任务与二级任务要区分角色

建议明确区分两类实体：

1. 一级链式支线任务（容器）
2. 二级流程任务节点（步骤）

一级任务负责：

- 链标题
- 总完成状态
- 当前激活到哪一步

二级任务负责：

- 当前步骤的实际目标
- 描述
- 奖励
- 地点
- 接受者 / 完成者

### 3.3 顺序推进只允许前进，不允许并行

本次第一版只做：

- 串行链
- 单当前节点
- 完成一个，发布下一个

不做：

- 多分支并行
- 分支条件选择
- 回退节点
- 可选分叉树

也就是说，这次虽然用户口头说“分支”，实际要做的是：

- **链式阶段任务**
- 不是树状分支任务系统

### 3.4 UI 先支持一层嵌套，不做无限层级

本次只支持：

- 一级支线任务
  - 二级流程任务标签

不做：

- 二级下再嵌三级
- 任意深度树形任务 UI

## 4. 建议数据结构

## 4.1 在 `QuestData` 基础上增加链式任务可选字段

文件：

- `TS/系统/08．任务系统/01．任务数据.ts`

建议新增可选字段：

```ts
export interface QuestChainStepData {
  id: string;
  title: string;
  description: string;
  objectives: QuestObjective[];
  rewards: QuestReward[];
  zone?: string;
  startNpc?: string;
  endNpc?: string;
  icon?: string;
  requireItem?: string;
  targetUnit?: string;
  requireCount?: number;
  progressText?: string;
  accepterName?: string;
  completerName?: string;
}

export interface QuestData {
  // 现有字段...

  chainMode?: "none" | "sequential";
  chainSteps?: QuestChainStepData[];
  currentChainStepIndex?: number;
}
```

说明：

- 普通任务：
  - `chainMode` 不填或 `"none"`
- 链式支线任务：
  - `chainMode = "sequential"`
  - `chainSteps = [...]`

### 4.2 运行时状态建议

不要只在配置层存链步骤，运行时也要明确保存：

- 当前激活到第几步
- 各步骤是否已完成
- 当前展开的是一级任务还是某个二级步骤

建议新增运行时结构，例如：

```ts
export interface QuestChainRuntimeState {
  activeStepIndex: number;
  completedStepIds: string[];
  expandedStepId?: string | null;
}
```

并将其挂在 `QuestData` 运行时实例上，或由 `questDB` 单独维护。

## 5. 配置层改造方案

### 5.1 不要打散成 5 条普通支线任务

不要简单把：

- 击杀哥布林
- 击杀哥布林法师
- 击杀哥布林精英

拆成 5 个普通支线 quest 再用 `requiredQuests` 串起来。

原因：

- UI 上会被当成 5 条普通平级支线任务
- 无法天然挂在同一个一级支线任务标题下面
- 展开态、完成态、接受者/完成者归属会很乱

### 5.2 正确做法

在 `TS/系统/08．任务系统/00．配置表/02．任务配置表.ts` 中，为一级支线任务配置：

```ts
{
  requireID: 20001,
  name: "剿灭哥布林洞窟",
  type: "链式支线",
  chainMode: "sequential",
  chainSteps: [
    { id: "goblin_step_1", title: "击杀20只哥布林", ... },
    { id: "goblin_step_2", title: "击杀哥布林法师×20", ... },
    { id: "goblin_step_3", title: "击杀哥布林精英×3", ... },
    { id: "goblin_step_4", title: "击杀哥布林大祭司", ... },
    { id: "goblin_step_5", title: "击杀哥布林王", ... },
  ]
}
```

说明：

- 一级任务只有一条配置
- 二级步骤放在 `chainSteps`
- 以后若要做更多类似任务，可直接扩展

## 6. 任务管理器改造

文件：

- `TS/系统/08．任务系统/01．任务管理器/04．QuestManager.ts`
- `TS/系统/08．任务系统/01．任务数据.ts`

### 6.1 接受任务时

一级链式支线任务被接受时：

- 任务本体进入 `IN_PROGRESS`
- 初始化 `activeStepIndex = 0`
- 仅第一步作为当前激活步骤

### 6.2 更新进度时

当前步骤完成时：

- 标记该步骤完成
- 若存在下一步：
  - `activeStepIndex += 1`
  - 下一步进入激活状态
  - 刷新 UI
  - 触发“下一步骤已发布”的提示
- 若不存在下一步：
  - 一级任务整体完成
  - 走现有 `onQuestCompleted(...)`

### 6.3 不建议完全复用当前 `updateObjective(...)`

当前 `updateObjective(...)` 的语义是：

- 更新 quest.objectives 某一项
- 如果这一条 quest 的 objectives 全完成，则直接 completeQuest

对于链式支线任务，这个逻辑不够用。

建议：

1. 保留普通任务旧逻辑
2. 新增链式任务专用推进逻辑，例如：

```ts
updateChainStepObjective(...)
advanceChainStepIfCompleted(...)
completeChainQuestIfLastStep(...)
```

### 6.4 UI 刷新回调要带上一级 questId 即可

UI 层不必单独暴露“二级步骤事件总线”。

这次建议仍使用：

- `triggerUIRefresh(playerId, questId)`

但 UI 构建数据时，看到该 `questId` 是链式任务，就展开其 `chainSteps` 渲染结构。

## 7. UI 改造方案

文件重点：

- `TS/系统/08．任务系统/02．任务UI拆分/02．任务UI辅助.ts`
- `TS/系统/08．任务系统/02．任务UI拆分/08．任务UI列表控制.ts`
- `TS/系统/08．任务系统/02．任务UI拆分/10．任务UI列表控制辅助.ts`
- `TS/系统/08．任务系统/02．任务UI拆分/12．任务UI预设构建.ts`
- `TS/系统/08．任务系统/02．任务UI拆分/14．任务UI列表帧构建.ts`

### 7.1 不要把一级任务和二级步骤混在同一行结构里硬拼

建议引入“列表渲染模型”，而不是直接对 `QuestData[]` 硬渲染。

建议在 UI 层先构造：

```ts
type TaskUIListNode =
  | { kind: "quest"; quest: QuestData }
  | { kind: "chainStep"; parentQuestId: string; stepId: string; ... };
```

然后支线列表构造时：

- 普通支线任务 -> 一个 `quest` 节点
- 链式支线任务 -> 一个 `quest` 父节点 + 若干 `chainStep` 子节点

### 7.2 一级任务行

一级链式支线任务行负责显示：

- 任务标题
- 总状态（进行中 / 完成）
- 可选：当前步骤概览

### 7.3 二级任务标签行

二级步骤行负责显示：

- 步骤标题
- 当前是否为激活步骤
- 是否已完成
- 点击后展开自己的详情

### 7.4 二级步骤详情展开

点击二级步骤标题后，展开区域显示：

- 任务描述
- 发布任务的 NPC
- 任务奖励
- 任务地点
- 接受任务的玩家
- 完成任务的玩家

这里建议沿用现有详情文本构建 helper：

- `buildRewardText`
- `buildInfoText`

但新增步骤级别版本，避免直接把 `QuestData` 和 `QuestChainStepData` 强绑死。

### 7.5 二级步骤行不要头像图标

当前 `isQuestWithRowIconLayout(...)` 是按 quest 行判断是否保留图标位。

本次需要新增：

- 对 `chainStep` 节点，固定走“无头像图标布局”
- 只保留底板 / 边框 / 文本

不要复用现有主任务行的头像排版。

### 7.6 展开状态建议分离

当前任务 UI 只有“展开某个 questId”的单一概念。

本次要区分：

- 一级 quest 展开
- 二级 step 展开

建议增加新的展开 key 规则，例如：

- 一级：`quest:<questId>`
- 二级：`step:<questId>:<stepId>`

这样不容易和现有展开态冲突。

## 8. 推荐实施顺序

### 阶段一：数据与运行时

1. 扩展 `QuestData` / `QuestChainStepData`
2. 为链式支线任务补配置样例
3. 扩展 `questDB` / `QuestManager` 运行时状态
4. 实现“步骤完成 -> 自动发布下一步 -> 最终完成父任务”

验收：

- 纯逻辑层可正确推进 5 步链式支线

### 阶段二：UI 数据构建

1. 在 UI 辅助层新增列表节点模型
2. 支线列表改为“普通 quest + chainStep 节点”的混合输出
3. 保持主线/日常列表逻辑不变

验收：

- 支线页能出现一级任务 + 二级步骤标签结构

### 阶段三：UI 视觉与交互

1. 新增二级步骤行的无头像布局
2. 新增步骤详情展开
3. 调整点击映射与展开状态键

验收：

- 二级步骤标题可点开
- 展开内容正确
- 不影响原有普通任务展开

### 阶段四：回归

1. 普通支线任务回归
2. 主线任务回归
3. 日常任务回归
4. 支线链式任务逐步推进回归

## 9. 禁止事项

1. 不要把二级流程任务直接伪装成 `objectives`
2. 不要把 5 个步骤拆成 5 个普通平级 quest 交给 UI 硬分组
3. 不要一次性重写整个任务 UI 模块
4. 不要改动主线 / 日常的现有渲染结构，除非是共享 helper 的最小补丁
5. 不要在本轮引入“任意深度任务树”

## 11. 验收标准

### 代码层

1. 普通任务仍然维持原数据结构与 UI 行为
2. 链式支线任务具备独立 `chainSteps`
3. 任务管理器能顺序推进子步骤
4. UI 层能区分一级 quest 节点与二级 step 节点
5. 二级步骤行不使用头像图标布局

### 功能层

以“剿灭哥布林洞窟”为样例：

1. 接受一级支线任务后，只激活第 1 步
2. 第 1 步完成后，自动发布第 2 步
3. 每一步都能点击展开详情
4. 最后一步完成后，一级支线任务整体完成
5. 一级任务状态、二级步骤状态、奖励、接受者/完成者显示正确

### 构建层

1. `npm run build` 通过
2. 若修改了回调 / helper / UI wrapper，必须检查生成 Lua
