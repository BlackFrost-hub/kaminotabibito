# 对话框系统异步安全收敛方案

## 1. 结论

当前对话框系统的异步安全等级，**还不建议视为 99.9% 档**。

主要原因：

- `~` 跳过仍走 `sync=true` 键盘回调，且回调里直接裁剪 `queue`
- 接受/拒绝任务回调里直接改共享播放状态，再立刻执行业务回调
- 对话播放链里“共享语义状态”和“本地显示状态”还没有彻底拆开
- 仍残留少量裸 `CreateTimer/TimerStart/DestroyTimer`

补充说明：

- `任务UI 不随对话框任务接受/提交通知刷新` 这个问题，已由 [对话框-任务UI联动修复报告.md](</C:/Users/Administrator/Desktop/syzl/规划文档/对话框-任务UI联动修复报告.md:1>) 记录并修复
- 修复方式是让对话框任务路径显式调用 `questManager.triggerUIRefresh(playerId, questId)`
- 这条修复应视为**保留项**，后续对话框重构时不能再回退到“空刷新函数”或绕开 `questManager` 的 UI 刷新桥

所以当前状态更接近：

- 主结构：方向正确
- 安全性：中高
- 工程稳定性：还没收敛到“长期不容易被后续改坏”的程度

## 2. 目标

把对话框系统收敛到下面这个模型：

> **同步层只维护每玩家一槽的语义状态；本地层只负责纯显示、幂等、只读操作。**

这里的“每玩家一槽”不是“只在自己客户端维护自己的槽”，而是：

- 全房所有客户端都对称维护 `slot[0..3]`
- `slot[i]` 的业务语义只服务 `Player(i)`
- 本地客户端只显示自己的那一槽

这套模型才是本项目里最稳的 N 槽落地方式。

## 3. 目标分层

### 3.1 同步层

同步层允许存在模块级全局表，但必须是**全端对称维护**的每玩家槽位状态。

建议统一收口为 `g_dialogRuntimeByPid[pid]` 一类结构，里面只放：

- `queue`
- `currentEntryIndex` 或等价头部语义
- `typingProgress`
- `typingLength`
- `phase`
- `waitingContinue`
- `questEntryIndex`
- `questContextId`
- `isActive`
- `canShowSemantic`
- `npcOccupationContext`

这些字段的要求：

- 所有客户端同路径写入
- 所有客户端同次数推进
- 不在 `GetLocalPlayer()` 内写
- 不在 `sync=false` 输入回调里写

### 3.2 本地显示层

本地显示层只读同步层，允许每个客户端只操作自己可见的那套 frame。

本地层只允许做：

- `DzFrameShow` / `DzFrameHide`
- 本地音效
- 本地提示文本显示
- 纯只读判定
- 纯幂等视觉刷新
- 本地 hover / hint / continue 提示闪烁

本地层禁止做：

- 改 `queue`
- 改任务接受/拒绝语义
- 改当前条目推进
- 改 NPC 占用 / 释放
- 改任何会被后续同步链继续消费的状态

### 3.3 任务 UI 联动桥

对话框系统后续重构时，必须明确保留一条稳定桥：

- 对话框任务接受
- 对话框任务完成提交
- 对话框任务失败或状态切换

这些路径只要影响任务数据，就必须显式通知 `questManager` 刷新 UI。

推荐固定规则：

- 任务数据写入：仍由任务/对话框业务层负责
- UI 刷新派发：统一走 `questManager.triggerUIRefresh(playerId, questId?)`
- 不允许再放“空函数占位，假定别处会自动刷新”

这条规则的目的是：

- 保持对话框路径与 JASS bridge 路径的 UI 刷新语义一致
- 避免后续重构时再次出现“数据已变，但任务 UI 不刷新”

## 4. 当前代码里的问题归类

### 4.1 已经接近正确的部分

- `showDialogFrames`
- `showQuestButtons`
- `showContinueHint`
- 按玩家播放打开音效
- 对话框任务接受/提交后，显式通过 `questManager.triggerUIRefresh(playerId, questId)` 触发任务 UI 刷新

前四项基本属于“本地显示层”。  
最后一项虽然不是本地显示层，但它是**正确的全端同步业务桥**，应保留。

### 4.2 仍然混层的部分

下面这些现在还不应算“纯本地链”：

- `skipDialogLocal`
- `runQuestAcceptForPlayer`
- `runQuestRejectForPlayer`
- `advanceDialog`
- `playEntry`
- `skipTyping`

原因：

- 它们不仅改显示
- 还会改 `queue`
- 还会改 `strNow/strLen`
- 还会改 `waitingClick/clickCooldown/isActive`
- 还会触发任务业务回调

### 4.3 当前最危险的点

#### A. `sync=true` 的 `~` 跳过直接裁剪 `queue`

这是当前最该优先处理的点。

本质问题不是 `~` 本身，而是：

- 同步输入回调里直接做共享状态重写
- 还把“跳到最后一条普通对话 / 跳到任务条目”的视觉策略写进了共享状态

这样一来，只要某端在此前已有轻微状态偏差，`skip` 会立刻放大差异。

#### B. 接受/拒绝任务回调的“先改状态，再执行业务回调”

这条链不是必炸，但重入敏感。

典型风险：

- 旧对话还在收尾
- `onAccept/onReject` 又 reopen 新对话
- `onFinish`、NPC 占用释放、气泡调度、任务 UI 刷新交错

它容易出现“逻辑没错但顺序越来越难证明”的情况。

#### C. 显示内容更新还没有明确归口

例如：

- `DzFrameSetText`
- `DzFrameSetTexture`
- `DzFrameSetFont`

这些操作今天大多还在全端对称链里做，因此短期不是主风险；但接口层没有明确边界，后续维护者很容易把它们错误地下放到本地输入链里。

#### D. 对话框任务路径和任务 UI 刷新桥不能再次脱钩

这个问题已经实际发生过，修复报告见：

- [对话框-任务UI联动修复报告.md](</C:/Users/Administrator/Desktop/syzl/规划文档/对话框-任务UI联动修复报告.md:1>)

问题本质：

- 对话框接受任务走的是 `setQuestState()` / 对话框业务链
- 它没有天然经过 `questManager.onQuestAccepted/onQuestCompleted`
- 如果对话框路径不显式补 `questManager.triggerUIRefresh(playerId, questId)`，任务 UI 就会滞后

因此这件事在异步安全上不属于高危 desync，但在系统设计上属于**必须固化的联动边界**。

## 5. 目标架构

### 5.1 语义状态机

建议把每玩家槽位的运行状态统一成有限状态机，而不是散落的布尔位：

- `idle`
- `typing`
- `waiting_continue`
- `waiting_quest_choice`
- `closing`

字段建议：

```ts
interface DialogSemanticState {
  playerId: number;
  isActive: boolean;
  phase: "idle" | "typing" | "waiting_continue" | "waiting_quest_choice" | "closing";
  queue: DialogEntry[];
  currentIndex: number;
  typingProgress: number;
  typingLength: number;
  activeQuestIndex: number;
  activeQuestContextId: number;
  canShowSemantic: boolean;
}
```

原则：

- 不再让 `waitingClick + clickCooldown + strNow + queue[0].isQuest` 这种组合隐式表达阶段
- 所有推进动作都先改 `phase`
- 本地显示层只根据 `phase` 渲染

### 5.2 本地显示缓存

本地层允许有纯显示缓存，但它必须不参与业务决策。

例如：

```ts
interface DialogLocalViewState {
  visible: boolean;
  lastRenderedEntryId: number;
  continueHintVisible: boolean;
  skipHintVisible: boolean;
  localHoverState: number;
}
```

这类状态可以只在本机维护。

要求：

- 不反哺同步层
- 不驱动任务接受/拒绝
- 不驱动 `queue` 推进

## 6. 输入链重构方案

### 6.1 `~` 跳过改成本地输入 + 同步语义命令

目标不是让 `~` 完全本地化，而是让它**不再直接在同步输入回调里做复杂状态修改**。

建议拆成两段：

#### 方案 A：最稳妥

- `~` 本地按键注册为 `sync=false`
- 本地只发“我要跳过”的低频同步命令
- 同步命令处理器只做极小语义推进

例如只允许：

- `typing -> waiting_continue`
- `typing -> waiting_quest_choice`

禁止同步命令处理器直接做：

- `queue = [last]`
- 重算立绘
- 重写标题正文

#### 方案 B：保留 `sync=true`

如果坚持保留 `sync=true`，也必须收敛成：

- 回调里只推进 `phase`
- 不做 `queue` 裁剪
- 不做复杂分支快进

也就是把现在的“视觉快进策略”改成“语义快进一步”。

### 6.2 面板点击继续

当前点击继续已经比 `~` 安全，因为它主要是单步推进。

但仍建议统一成：

- 同步层：`tryAdvanceSemanticState(pid)`
- 本地层：`renderDialogForLocalPlayer(pid)`

不要让 frame 回调直接混写显示和语义。

### 6.3 接受/拒绝任务

接受/拒绝应该改成“两段式”：

#### 第一段：同步层提交选择

- 锁定当前 `questContextId`
- 校验当前 `phase === waiting_quest_choice`
- 记录 `selectedChoice = accept/reject`
- 关闭当前语义态

#### 第二段：业务层执行

- 通过稳定 `questContextId` 找到业务回调
- 执行业务逻辑
- 如需 reopen，对外走统一入口

这样可以避免直接从 frame 回调里一边 splice 队列，一边立刻钻进业务 reopen 链。

## 7. 渲染链重构方案

### 7.1 统一成“同步刷新数据，本地统一渲染”

建议形成固定调用序：

1. 同步层推进语义状态
2. 标记 `renderDirty[pid] = true`
3. 本地渲染器轮询或被动消费 dirty
4. 本地只渲染自己的 `pid`

渲染器做的事：

- 根据语义状态决定是否显示面板
- 根据当前条目决定标题正文
- 根据当前条目决定立绘贴图
- 根据 `phase` 决定显示继续提示还是任务按钮

这里最关键的一点是：

> **渲染器不改语义状态，只消费语义状态。**

### 7.2 文本/贴图更新的边界

长期目标建议是：

- `DzFrameSetText/SetTexture/SetFont` 只从统一渲染器出去
- 业务逻辑层不直接摸 frame

这样以后审计异步风险时，只需要检查：

- 语义推进函数
- 本地渲染函数

而不是满系统找散落的 `DzFrameSetText`。

## 8. Timer 收敛方案

当前主打字机 timer 已经较好，但 skip 冷却和部分旁路 timer 还不统一。

建议：

- 一发式 timer 全部走 `safeTimerStart / safeDestroyTimer`
- 周期语义 tick 尽量统一到对话框中心 tick
- 本地纯显示闪烁若需要 timer，必须明确标注为本地只读视觉 timer

原则：

- 业务语义 timer：全端对称
- 本地视觉 timer：只读、不反哺同步层

## 9.1 推荐执行顺序

为了避免中途把系统改成“半新半旧”状态，执行顺序固定为：

1. 第 1 步：skip 止血
2. 第 2 步：抽语义阶段字段
3. 第 3 步：抽本地渲染器
4. 第 4 步：accept/reject 两段式
5. 第 5 步：文档固化

不建议跳步：

- 不要先抽渲染器再处理 skip
- 不要先改业务 reopen 再不管任务 UI 刷新桥

## 9.2 每步提交要求

建议每一步都独立完成以下检查：

- TS 编译通过
- 生成 Lua 后检查对应文件是否仍是具名回调、无新增匿名闭包进 JASS
- 检查任务 UI 刷新链是否还在
- 检查 `sync=true` 路径是否仍只做收敛后的最小语义推进

如果执行人要拆多次提交，建议按“第 1 步到第 5 步”分提交，不要把所有改动揉成一坨。

## 10. 验收标准

达到目标后，应满足下面这些标准：

- `GetLocalPlayer()` 分支里不再改 `queue`
- `GetLocalPlayer()` 分支里不再改任务语义状态
- `sync=true` 输入回调里不再直接裁剪 `queue`
- 任务 accept/reject 不再直接在 frame 回调里混做“状态裁剪 + reopen”
- frame 内容更新统一走渲染器
- 本地层只做显隐、音效、只读和幂等视觉刷新
- 对话框任务路径不会再绕开 `questManager.triggerUIRefresh(playerId, questId?)`

额外验收：

- `20．对话框渲染-任务回调与命中.ts` 中，skip/accept/reject 三条高风险链已能一眼分辨同步逻辑和本地显示逻辑
- 对话框相关新增文件或改动文件没有把匿名闭包直接挂进 JASS / Dz 注册点
- 任务接受后 UI 立即出现任务
- 任务提交后 UI 立即移除或刷新对应任务

## 11. 对“99.9%”的判断

如果只做第 1 步，系统会比现在稳很多，但仍不建议宣称 99.9%。

如果做到：

- skip 收敛
- 接受/拒绝两段式
- 同步语义态 / 本地显示态彻底分层
- timer 和渲染出口统一

那这套对话框系统才比较接近本项目里可以接受的 **99.9% 工程安全档**。

注意这里仍是工程意义上的高置信，不是数学意义上的绝对安全。  
Lua / Dz / 联机 UI 本身就不适合宣称 100%。

## 12. 推荐最终原则

最后统一成一句话：

> **每玩家一槽的语义状态，全端对称维护；每玩家一套本地显示，只做显隐、幂等、只读操作。**

对话框系统后续所有改动，都以这句话作为审查标准。
