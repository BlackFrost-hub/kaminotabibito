# DOT 与 Buff 表表索引整改规划

## 1. 文档用途

本文件是执行文档，不是讨论稿。

适用对象：

- 后续接手实现的开发者
- 执行代码修改的 AI
- 最后做代码审查和联机安全验收的人

使用方式：

1. 先完整阅读本文。
2. 按本文的阶段顺序实施，不要跳步混改。
3. 每完成一个阶段，回填本文末尾的“执行回填区”。
4. 实现完成后，再交给主审做联机安全审查和功能验收。

---

## 2. 背景与问题定义

当前项目里，`DOT` 系统和 `Buff` 系统都存在“表表索引 + 动态遍历”的结构。

典型形态：

```ts
stateByType[typeId][hid] = true;
unitToBuffs[hid].buffs[buffId] = state;
```

单纯的二级索引本身不是立即错误。真正的风险来自下面几条叠加：

1. 运行时动态创建对象
2. 高频路径读写
3. 使用 `for...in` / 对象枚举
4. 枚举顺序可能影响后续状态推进、同步或伤害结算

在联机项目里，**动态对象的枚举顺序不应作为逻辑正确性的基础**。  
因此本次整改的核心目标不是“禁止一切二级索引”，而是：

- 去掉不稳定枚举
- 保证遍历顺序稳定
- 把高频同步路径中的状态推进建立在稳定序列上

---

## 3. 风险分级结论

### 3.1 高优先级：DOT 系统

重点文件：

- `TS/系统/04．伤害系统/01．DOT定义/05．DOT状态同步.ts`
- `TS/系统/04．伤害系统/01．DOT定义/06．DOT执行器.ts`
- `TS/系统/04．伤害系统/01．DOT定义/07．DOT施加策略.ts`

当前风险不是只来自：

- `stateByType[typeId][hid]`
- `ignoredTargetByType[typeId][hid]`

更大的风险在于：

- `05．DOT状态同步.ts` 中对动态表做双层遍历
- 遍历结果继续驱动同步状态推进或伤害结算

这组问题应视为**优先立即治理**。

### 3.2 中优先级：Buff 系统

重点文件：

- `TS/系统/05．Buff系统/00．Buff系统.ts`

当前结构例如：

- `unitToBuffs[hid].buffs[buffId]`

风险核心不是索引写入本身，而是：

- 双层 `for...in` 遍历 `unitToBuffs`
- 再遍历 `.buffs`

如果保留对象索引结构，但遍历改成稳定序列，这组风险可以明显下降。

---

## 4. 本次整改目标

### 4.1 结构目标

- 不再让 `for...in` 直接遍历动态对象作为主逻辑路径
- 遍历必须基于稳定顺序
- 高频同步路径不依赖对象枚举顺序

### 4.2 行为目标

- DOT 伤害推进逻辑不变
- Buff 生命周期逻辑不变
- Buff / DOT 的外部接口尽量不变
- 不顺手重写整个伤害系统或 Buff 系统

### 4.3 联机目标

- 不在同步主路径里使用不稳定对象枚举
- 不把状态推进建立在 Lua 对象键枚举顺序上
- 对于需要全端一致推进的列表，统一生成稳定序列

---

## 5. 明确禁止事项

以下事项本次一律禁止：

1. 禁止顺手重写整个 DOT 系统
2. 禁止顺手重写整个 Buff 系统
3. 禁止把本次整改与 unrelated 格式化、命名重排、注释清洗混在一起
4. 禁止引入新的“为了规避遍历问题而更复杂的全局魔法层”
5. 禁止继续增加新的 `for...in` 动态对象遍历
6. 禁止把“暂时没炸”当成保留不稳定结构的理由

---

## 6. 推荐整改原则

### 6.1 原则一：保留存储结构，先收遍历

本次优先策略不是立刻把所有：

```ts
Record<number, Record<number, T>>
```

改成另一套复杂容器。

优先做法是：

- 保留当前存储结构
- 先把遍历收成稳定列表

也就是先解决“最危险的部分”，而不是一次性推翻全部数据结构。

### 6.2 原则二：稳定顺序优先

如果必须遍历对象键，执行前必须：

1. 取出 key 列表
2. 转为数值或稳定字符串
3. 做稳定排序
4. 再按排序后的列表遍历

禁止直接：

```ts
for (const k in table) { ... }
```

### 6.3 原则三：高频路径不要隐式分支

高频 DOT / Buff 推进路径里，执行顺序必须肉眼可见。

推荐形态：

```ts
const typeIds = getSortedTypeIds(...);
for (let i = 0; i < typeIds.length; i++) {
  const typeId = typeIds[i];
  const targetIds = getSortedTargetIds(...);
  for (let j = 0; j < targetIds.length; j++) {
    ...
  }
}
```

不要把关键顺序藏在对象枚举里。

## 7. DOT 系统详细整改方案

### 7.1 第一阶段：定位所有动态遍历入口

执行者先在以下文件里确认并标注：

- `TS/系统/04．伤害系统/01．DOT定义/05．DOT状态同步.ts`
- `TS/系统/04．伤害系统/01．DOT定义/06．DOT执行器.ts`
- `TS/系统/04．伤害系统/01．DOT定义/07．DOT施加策略.ts`

需要重点寻找：

- `for...in`
- `Object.keys`
- 双层对象枚举
- 对枚举结果继续做同步推进/伤害执行/删除状态

交付要求：

- 在修改说明里明确写出“哪些遍历点已替换，哪些只是单点读写保留”

### 7.2 第二阶段：先改 `05．DOT状态同步.ts`

这一步优先级最高。

推荐改法：

1. 外层 `typeId` 不再直接枚举对象
2. 提供稳定的 `getSortedTypeIds(stateByType)` helper
3. 内层 `hid` 不再直接枚举对象
4. 提供稳定的 `getSortedHandleIds(tab)` helper

建议新增局部 helper：

```ts
function getSortedNumericKeys(obj: Record<number, any> | undefined): number[] {
  if (!obj) return [];
  const keys: number[] = [];
  for (const k in obj) {
    const n = tonumberCompat(k);
    if (n != null) keys.push(n);
  }
  keys.sort((a, b) => a - b);
  return keys;
}
```

要求：

- 外层顺序稳定
- 内层顺序稳定
- 删除逻辑不能破坏当前轮遍历

### 7.3 第三阶段：收 `06．DOT执行器.ts` / `07．DOT施加策略.ts`

这里分开看：

#### 可以暂时保留的部分

- 单点写入：
  - `tab[hid] = true`
  - `delete tab[hid]`

如果它们不直接依赖枚举顺序，可以先保留。

#### 必须检查的部分

- 写入是否发生在同步路径
- 写入后的读取是否依赖对象遍历顺序
- 删除是否和同步推进同时发生

建议：

- 先确保“读路径稳定”
- 再决定是否进一步替换存储结构

## 8. Buff 系统详细整改方案

### 8.1 第一阶段：定位双层遍历点

重点文件：

- `TS/系统/05．Buff系统/00．Buff系统.ts`

重点检查：

- `for...in unitToBuffs`
- `for...in unitToBuffs[hid].buffs`

### 8.2 第二阶段：保留结构，改稳定遍历

建议策略：

1. 保留：

```ts
unitToBuffs[hid]
unitToBuffs[hid].buffs[buffId]
```

2. 遍历时改成：

- 先收集 `hid`
- 数值排序
- 再收集 `buffId`
- 稳定排序（如果是数值 ID 按数值；如果是字符串 ID 按字典序）

推荐 helper：

```ts
function getSortedBuffHolderIds(): number[] { ... }
function getSortedBuffIds(buffs: Record<string, any>): string[] { ... }
```

### 8.3 第三阶段：不要扩大到 UI 层

本次只处理 Buff runtime 主状态表，不顺手把：

- `BuffUI`
- `BuffUIViewModel`
- 选择事件中心

再混进来。

这些链路已经走过一轮整改，不要因为本次遍历治理再引入回归。

---

## 9. 推荐新增 helper 的放置位置

优先建议：

- 局部 helper 先写在对应文件内

如果后面发现 DOT / Buff 都重复需要同类 helper，再提炼到：

- `TS/lib/扩展函数/封装函数/01．通用工具/08．Map安全遍历.ts`

但这一步不是本次必须目标。

本次目标是先把危险遍历点消掉，不是先做一个宏大抽象层。

---

## 10. 建议实施顺序

按下面顺序实施：

1. `DOT状态同步.ts`
2. `DOT执行器.ts`
3. `DOT施加策略.ts`
4. `Buff系统.ts`
5. 复扫全仓 `for...in` 在 DOT/Buff 目录下是否还残留

不要一开始同时改 DOT 和 Buff 全部文件，容易把回归来源搅乱。

## 11. 验收标准

### 11.1 代码层验收

1. `DOT` / `Buff` 目标文件中，不再存在关键同步主链的裸 `for...in` 动态对象遍历
2. 新增的稳定遍历 helper 逻辑清晰，可读，不搞魔法分发
3. 不引入新的匿名闭包进 JASS 引擎回调

### 11.2 构建验收

1. `npm run build` 通过
2. 不引入新的循环依赖
3. 生成 Lua 中关键同步主链的遍历顺序可读可检查

### 11.3 联机安全验收

1. DOT 周期伤害正常
2. Buff 生命周期正常
3. 不因 DOT / Buff 推进引入新的联机分叉

### 11.4 回归验收

至少回归以下内容：

1. DOT 叠加、刷新、到期清理
2. Buff 增加、覆盖、移除
3. BuffUI 显示是否仍正常
4. 伤害系统相关联动是否仍正常
